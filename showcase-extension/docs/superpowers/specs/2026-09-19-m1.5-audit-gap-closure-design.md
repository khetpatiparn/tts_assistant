### 1.3 ข้อสังเกตที่ตรวจแล้ว "ไม่เป็นปัญหา"

- **`context.on('request')` ครอบคลุม service worker จริง** ใน Playwright 1.63 — ยืนยันจาก source ที่ bundle มา
  (`ServiceWorker` ผูก `CRNetworkManager` ของตัวเองและ emit เข้าที่ browser context) ข้อกังวลที่ว่า
  page-level interception ไม่เห็น worker traffic จึง**ไม่ตรงกับเวอร์ชันที่ pin ไว้** — แต่ listener ถูกผูก
  *หลัง* fixture รอ service worker เสร็จ traffic ช่วง startup จึงอยู่นอกหน้าต่างการสังเกต
- **เส้นทาง Product ID ในโค้ดถูกต้องทุก hop** — ไม่มี `Number()`, `parseInt`, หรือการเทียบเชิงตัวเลขบน ID
  ที่ใดใน `extension/src` ช่องว่างของ E2 จึงเป็น **evidence gap ไม่ใช่ known defect**
- `chrome.storage` มี permission แต่ไม่มี call site — ไม่ใช่ข้อมูลรั่ว แต่ทำให้ข้อความใน README เป็นเท็จ

## 2. การตัดสินใจที่ล็อกแล้ว

1. **เพิ่มปุ่มล้างข้อมูลใน dashboard** และปฏิเสธการล้างขณะมี run ทำงานอยู่ (ผู้ใช้เลือก)
2. **ทำครบทั้ง 6 กลุ่ม** WP1–WP6 (ผู้ใช้เลือก)
3. **ไม่ประดิษฐ์ TTL ใหม่** — spec มี TTL ที่เดียวคือ §8.4 "retention ที่เสนอ 7 วัน" สำหรับ *raw debug sample*
   ซึ่ง build นี้ไม่เคย persist เลย (`bodyText` อยู่ใน memory เท่านั้น) จึงเป็น **NOT APPLICABLE** ไม่ใช่ช่องว่าง
   ส่วน normalized staged rows ไม่มี TTL ตาม design และถูกจำกัดด้วย per-run cap + เส้นทางล้างที่ชัดเจนแทน
4. **ไม่ขยาย threshold ใด ๆ** เพื่อให้ผ่าน — D1 แก้ที่กลไก ไม่ใช่ที่เกณฑ์
5. **ไม่ implement permission flow เพื่อปิด UI06** ในรอบนี้

## 3. WP1 — Progress และ Cancel latency

**เกณฑ์ (spec:728):** progress หลัง commit หน้า ≤1 วินาที; Cancel หยุดการเริ่ม request ใหม่ทันที
และ UI เปลี่ยนสถานะ ≤2 วินาที บนเครื่องทดสอบที่บันทึกสเปก

spec ไม่ได้นิยามจุดเริ่ม/สิ้นสุดการวัด รอบนี้จึงนิยามให้ชัดและบันทึกนิยามไว้ในผลทดสอบ:

| | นิยาม |
|---|---|
| **จุดเริ่ม (progress)** | วินาทีที่ transaction ของ `commitPage` สำเร็จใน service worker บันทึกเป็น `Date.now()` ณ ขณะนั้นลงบน run checkpoint เป็นฟิลด์ `lastCommitAt` |
| **จุดสิ้นสุด (progress)** | วินาทีที่หน้า dashboard แสดงจำนวน staged ใหม่ใน `#run-status` อ่านด้วย `Date.now()` ในบริบทของหน้า |
| **จุดเริ่ม (cancel)** | วินาทีที่ test คลิกปุ่ม Cancel |
| **จุดสิ้นสุด (cancel)** | วินาทีที่ `#run-status` แสดงสถานะ `cancelled` |

นาฬิกาทั้งสองฝั่งเป็นนาฬิกาเครื่องเดียวกัน ค่าต่างจึงมีความหมาย

**กับดักที่ต้องเลี่ยง:** ห้ามวัดเฉพาะ "เวลาที่ข้อความ `#run-status` เปลี่ยน" แล้วเรียกว่า latency —
นั่นคือการวัดคาบ poll ไม่ใช่ commit→display จุดยึด `lastCommitAt` คือสิ่งที่ทำให้เป็นการวัดจริง
และห้ามใช้เวลารวมของ E2E แทน latency ของ UI

**การแก้ production**

- `RunCheckpoint` เพิ่ม `lastCommitAt: number | null` เขียนภายใน transaction ของ `commitPage`
- `ResumeState` และ response ของ `run.status` ส่งค่านี้ต่อถึงหน้า
- ลดคาบ poll ของ dashboard จาก 1000 ms ลงให้ต่ำกว่างบอย่างมีระยะเผื่อ (เสนอ **250 ms**) —
  งานต่อรอบคือ count query เดียว ต้นทุนต่ำ
- แก้ D2: runner เรียก `store.heartbeat(runId, generation, now)` หลัง `commitPage` สำเร็จทุกครั้ง
  เพื่อให้ lease ไม่หมดอายุระหว่าง run ยาว (progress จึงเดินต่อ และ `resume.kind` ยังเป็น `running` ตามจริง)
- `PAGE_INTERVAL_MS = 1000` ใน runner เป็นการหน่วงของ mock ไม่ใช่ค่าคงที่ของ product — คงไว้

**การทดสอบ**

- E2E ใหม่: วัด progress ทุกครั้งที่จำนวน staged เพิ่ม เทียบ `observedAt − lastCommitAt ≤ 1000` และบันทึกค่าสูงสุดที่วัดได้
- E2E ใหม่: Cancel — วัดจากคลิกถึง `cancelled` เทียบ ≤ 2000 ms พร้อมยืนยันว่าไม่มี request เพิ่มหลัง cancel
- Unit: regression ว่า runner เรียก heartbeat ทุก commit และ lease อยู่รอดเกิน TTL ระหว่าง run ยาว
- ถ้าเกินงบ → **แก้สาเหตุแล้ววัดใหม่ ห้ามขยายงบ**

## 4. WP2 — Lifecycle บน browser จริง

**Task ศูนย์ (spike, ต้องทำก่อน):** หยุด MV3 service worker จาก Playwright 1.63 ได้หรือไม่

ข้อเท็จจริงที่มีแล้ว: `Worker` ของ Playwright ไม่มี API หยุด worker; CDP domain `ServiceWorker` มี
`stopWorker`/`stopAllWorkers` อยู่ใน protocol ที่ bundle มา; `context.newCDPSession()` รับ `Page`/`Frame`

ลำดับการลอง: (1) `context.newCDPSession(page)` → `ServiceWorker.enable` → `ServiceWorker.stopAllWorkers`
(2) ถ้าไม่ได้ ลองผ่าน `chrome://serviceworker-internals/`
(3) ถ้าไม่ได้ทั้งคู่ → บันทึก LC03 ระดับ browser เป็น **BLOCKED พร้อมเหตุผลที่พิสูจน์แล้ว** และ
relabel หลักฐาน unit เดิมว่าเป็น simulation — **ห้ามแทนที่ด้วย simulation แล้วเรียกว่า browser E2E**

**การแก้ production (D3)**

- ใน `run.status`: เมื่อ in-memory registry ไม่มี active run แต่ checkpoint ยังถือ lease ที่ยังไม่หมดอายุและยังไม่ released
  ให้รายงานว่า **interrupted** ไม่ใช่ running
  - เหตุผลที่ปลอดภัย: MV3 มี service worker เดียวต่อ extension และ dashboard ทุกแท็บใช้ตัวเดียวกัน
    registry ที่ว่างพร้อม lease ที่ยังมีชีวิตจึงแปลว่า worker เจ้าของหายไปแล้วเท่านั้น
  - ข้อนี้**ไม่ทำให้ LC01 อ่อนลง**: แท็บที่สองเห็น registry เดียวกัน จึงยังถูกปฏิเสธด้วย `already_running` ตามเดิม
- `run.start` ต้องรับช่วง lease ที่กำพร้าได้ เพื่อไม่ให้ผู้ใช้ติดตาย (ตรงกับ LC06 "เสนอ scan ใหม่จาก 0")
- dashboard: กิ่ง idle ต้องแสดงกรณี interrupted ทั้งแบบ `interrupted` และแบบ `running` ที่กำพร้า

**การทดสอบ**

- LC06 ระดับ browser: ใช้ user-data dir จาก `fs.mkdtemp` ใน temp ของระบบ — launch → เริ่ม scan → ปิด context →
  launch ซ้ำที่ dir เดิม → ยืนยันว่า UI เสนอ scan ใหม่จาก 0 และไม่อ้างว่า completed
  **ห้ามชี้ไปที่ browser profile จริงของผู้ใช้เด็ดขาด**
- LC03 ระดับ browser (ถ้า spike ผ่าน): commit หน้าแรก → หยุด worker จริง → เปิด dashboard →
  ยืนยันว่าเห็นสถานะ interrupted พร้อมจำนวน staged ที่ถูกต้อง ไม่ค้าง Running ไม่ falsely complete และ Start ใช้ได้
- แก้ T1: แทน assertion ที่ fail ไม่ได้ ด้วย assertion ที่ตรวจว่า run ใหม่ขอ offset 0 จริงจาก adapter
  และแถว staged ของ run เก่าไม่ถูกผสมเข้ารายงานใหม่

## 5. WP3 — Clear data และ retention

**สิ่งที่ spec กำหนดจริง:** PK05 (P1, R11, spec:625) = "cache/fixtures retention และ Clear data —
ลบข้อมูลของ extension ตามที่แจ้ง โดยไม่ลบ cookie TikTok" และ G1 ข้อสุดท้าย (spec:729) ต้องมีเอกสาร clear data
spec **ไม่ได้บังคับ**ให้มีปุ่มใน extension — "ตามที่แจ้ง" ทำให้ README เป็นสัญญา

**การออกแบบ**

- message type ใหม่ `data.clear` — ไม่มีพารามิเตอร์ใด ๆ (คงกฎ strict schema: ไม่รับ URL/path/method จาก message)
- `CheckpointStore.clearAll()` — ลบทั้งสอง object store ใน **transaction เดียว**
- **การป้องกัน:** ปฏิเสธด้วย code เฉพาะเมื่อมี active run ใน registry หรือมี lease ที่ยังไม่หมดอายุและยังไม่ released
  - เหตุผล: ถ้าล้างเฉพาะ `products` โดย `runs` ยังอยู่ run ที่กำลังวิ่งจะ commit แถวกลับเข้ามาใหม่
    (fencing ปัจจุบันกัน run ที่แข่งกัน ไม่ได้กันการล้าง)
- dashboard: ปุ่ม "ล้างข้อมูลที่เก็บไว้" พร้อมการยืนยัน หลังสำเร็จให้ล้าง preview/selection state และแสดงสถานะว่าง

**การทดสอบ**

- Unit: ล้างแล้วทั้งสอง store ว่าง; ปฏิเสธเมื่อมี run ทำงานอยู่; fencing ยังทำงานถูกต้องหลังล้าง
- E2E: scan → มีข้อมูล → ล้าง → `run.status` ไม่มี active run และ staged = 0 → reload แล้วยังว่าง
- **ห้ามอ่าน cookie TikTok จริงเพื่อพิสูจน์ข้อนี้** — ครึ่ง cookie พิสูจน์ด้วยขอบเขตโค้ด (ไม่มี permission `cookies`,
  ไม่มีการอ้างถึง `chrome.cookies` ใน bundle) ซึ่ง PK01/PK02 ครอบคลุมแล้ว

**จุดยืนเรื่อง retention ที่จะบันทึก (ไม่ประดิษฐ์ใหม่)**

- raw response body ไม่เคยถูก persist → TTL 7 วันของ §8.4 เป็น **NOT APPLICABLE** กับ build นี้
- normalized staged rows ไม่มี TTL ตาม design — ถูกจำกัดด้วย cap ต่อ run (20 MiB / 5,000 รายการ) และเส้นทางล้างที่ชัดเจน
- README ต้องแก้: ตัดข้อความ `chrome.storage` ที่เป็นเท็จ อธิบายปุ่มล้าง และระบุจุดยืน retention ข้างต้น

**PK05 หลังรอบนี้** แยกเป็นส่วนย่อยภายใต้ id เดิม: ครึ่ง Clear data ทดสอบอัตโนมัติได้,
ครึ่ง uninstall ยังเป็นหลักฐาน manual แยกไว้ชัด, ครึ่ง retention เป็นการระบุจุดยืนพร้อมเหตุผล **คง priority P1**

## 6. WP4 — ความน่าเชื่อถือของ network-isolation

ต้องแยกให้ออกระหว่าง "ไม่มี request เกิดขึ้นใน happy path" กับ "ตัวตรวจจับจับได้จริง" ปัจจุบันมีแต่ข้อแรก

**Positive control (E2E)** — test แยกที่มี listener ของตัวเอง: จากหน้า dashboard ยิง `fetch`
ไปที่ `http://127.0.0.1:<port ที่ปิดอยู่>` แล้วยืนยันว่า listener เห็น request นั้นจริง

- พิสูจน์ว่าตัวตรวจจับทำงาน โดย**ไม่มีอะไรออกจากเครื่อง** ไม่แตะ TikTok และไม่เพิ่ม permission ใด
- CSP ปัจจุบัน (`script-src 'self'; object-src 'self';`) ไม่มี `connect-src`/`default-src`
  จึงไม่บล็อก fetch และ request event เกิดขึ้นจริง — ข้อนี้ตรวจแล้ว
- ต้องยืนยันด้วยว่า assertion หลักจะ **fail** เมื่อมี request ต้องห้าม ไม่ใช่แค่ผ่านเมื่อไม่มี

**ทำให้ assertion หลักรัดกุมขึ้น**

- เลิก `return` ทิ้ง scheme ที่ไม่ใช่ http(s) — จำแนกด้วย "เป็น loopback หรือไม่" แทน "เป็น http(s) หรือไม่"
  เพื่อไม่ให้ `ws://`/`wss://` หรือ scheme อื่นรอด และระบุข้อยกเว้น loopback ไว้อย่างเปิดเผย
- เลิกใช้ `.includes('tiktok')` เป็นนิยามความปลอดภัย — คงไว้ได้เป็น diagnostic รอง
  แต่ assertion หลักคือ "ไม่มี request ที่ไม่ใช่ loopback ไม่ว่า scheme ใด"
- ผูก listener ให้เร็วที่สุดเท่าที่ fixture ทำได้ และ**บันทึกอย่างเปิดเผย**ว่า traffic ช่วง SW startup
  ก่อน fixture พร้อม อยู่นอกหน้าต่างการสังเกต

**ฝั่ง Node guard**

- เพิ่ม test ที่พิสูจน์ว่า ledger ที่ไม่ว่าง **ทำให้ run แดงจริง** โดยเรียกตัวตรวจโดยตรง
  ไม่พึ่งลำดับของ `afterEach`
- บันทึกขอบเขตจริงของ guard: **ครอบคลุม** `fetch`/XHR/WebSocket/EventSource/`sendBeacon`
  และ TCP ที่ไม่ใช่ loopback (ซึ่งครอบ `node:http`/`node:https` ด้วย);
  **ไม่ครอบคลุม** `dns`, UDP/`dgram`, `child_process`, `worker_threads`, ปลายทาง loopback,
  การ connect ที่ไม่ระบุ port และการแทนที่ด้วย `Object.defineProperty`
  — `configurable: true` เป็นการตัดสินใจโดยเจตนา เพราะ jsdom teardown ลบ global เหล่านี้
- `npm run test:e2e` ไม่โหลด guard นี้ (คนละ runner) — เป็นเรื่องปกติและต้องระบุไว้ ไม่ใช่ข้อบกพร่องที่ซ่อน

## 7. WP5 — Lossless Product ID ตลอดเส้นทาง

ช่องว่างจริง: หลักฐานเลขเปล่ามีเฉพาะช่วง parse→normalize ใน Node ส่วน page → IndexedDB →
preview → selection → export **ไม่มีหลักฐานเลขเปล่าเลยทั้งระดับ unit และ E2E** และ E2E ที่ครอบเส้นทางเต็ม
รันบน fixture ที่ ID เป็น string อยู่แล้ว

**การออกแบบ**

- แก้ default mock catalog ให้บางแถวส่ง `product_id` เป็น **เลข 19 หลักไม่ใส่ quotes** โดย
  **คงแถวแรกเป็น string `'1736749159048840633'` เดิม** เพื่อไม่ทำลาย unit test ที่ pin ค่านี้ไว้
  - ต้องประกอบ body text ให้เลขเปล่ารอด (ใช้ `JSON.stringify` ตรง ๆ กับแถวเหล่านั้นไม่ได้)
  - เป็นการแก้ fixture ที่อยู่ใน mock adapter ซึ่งไม่เข้า release bundle (alias split ของ PK03)
    จึง**ไม่ได้เพิ่ม runtime switch** ที่หน้าเว็บสั่งได้
- แก้ T3: แทน assertion ที่อ้างอิงตัวเอง ด้วยการเทียบกับสตริงตัวเลขที่ hardcode ไว้ ตรวจกับไฟล์ export ที่ดาวน์โหลดจริง
- เพิ่ม assertion ใน E2E ว่า `hasLosslessJsonSupport()` เป็น true ใน runtime ของ extension จริง —
  พิสูจน์สมมติฐาน Chrome 124+ reviver ตรงจุดที่ใช้งานจริง ไม่ใช่แค่ใน Node
- **ตัดสินแล้วว่าไม่แก้:** `JSON.parse` ธรรมดาที่ `runner.ts:132,144` (identity + pagination metadata)
  คงไว้ตามเดิม — Product ID ไม่ได้อ่านผ่านเส้นทางนี้ และค่าที่อ่าน (`next_offset`/`total`) จะเสียความละเอียด
  ก็ต่อเมื่อเกิน 2^53 ซึ่งไม่ใช่สภาพที่เกิดได้จริง การแปลงจะไปแตะ pagination ซึ่งเป็นพื้นที่ P0 (PG01–PG17)
  โดยไม่ปิดช่องว่างใดที่ audit พบ จึงบันทึกเป็นข้อสังเกตในเอกสารแทนการแก้โค้ด

## 8. WP6 — เอกสารและ traceability

**กฎที่บังคับ**

1. ใช้เฉพาะ `NOT RUN` / `PASS` / `FAIL` / `BLOCKED` / `NOT APPLICABLE` — เลิกใช้ `PASS (บางส่วน)` ทุกที่
2. เมื่อ test id หนึ่งครอบสองครึ่ง ให้**คง id เดิม** แล้วแยกเป็นแถวย่อยที่มีสถานะถูกต้องของตัวเอง
   พร้อมประโยคอธิบายความสัมพันธ์ — **ไม่เปลี่ยนนิยาม requirement เดิม**
3. **PK04**: ครึ่งที่อยู่ใน scope (ไม่มี request ออกนอกเครื่อง) มีสถานะของตัวเอง;
   ครึ่ง "allowlisted read-only" บันทึกตามสภาพที่ยังไม่มี live adapter — **ไม่ถูกนับเป็น PASS เต็มรายการ**
4. **VA10** ออกจากรายการ blocker ของ G1 (G1 = VA01–VA09) บันทึกตาม spec:644 ว่าไม่จำเป็นต่อ M1 baseline
   เมื่อยังไม่เปิด optimization และ**ห้ามให้คะแนน PASS โดยยังไม่ทดสอบ**
5. **VA03** คง id เดียว ระบุว่าครึ่ง mock มีหลักฐานแล้ว (PG01/PG02) ครึ่ง live ยัง BLOCKED บน G0
6. ตัดข้อความ "ไม่มีอะไรให้ทำต่อในสภาพ mock-only" และ "ทุก item ที่ทำได้เสร็จหมดแล้ว"
7. **M1.5** ระบุขอบเขตที่ปิดแล้วและ gate ที่ยังค้าง ไม่เหมารวมว่า complete
8. **UI01–UI05** ระบุให้ตรงว่าข้อใดยืนยันระดับ browser และข้อใดเป็น jsdom/module
9. ลบข้อความเท็จเรื่อง `run.status` fallback (X7) และปรับ LC03/LC06 ให้ตรงระดับหลักฐานจริง
10. **UI06** ระบุเหตุผลให้ตรง: เลื่อนเพราะยังไม่ได้ implement permission handling ไม่ใช่เพราะต้องรอ response จริง
11. **PK05 คง priority P1**
12. แยก "ผลในอดีต" ออกจาก "สถานะล่าสุด" — รอบนี้เพิ่ม section ของตัวเองพร้อม environment,
    คำสั่งที่รันจริง และตัวเลขจริง **สิ่งที่ไม่ได้บันทึกไว้ในอดีตห้ามเดาย้อนหลัง**
13. แยก "mock prototype ตรวจครบตามขอบเขตใด" ออกจาก "live-ready G1" — **ห้ามเปลี่ยนเกณฑ์ G1 เพื่อให้ผ่าน**

**ไฟล์ที่กระทบ:** `docs/test-results.md`, `docs/traceability.md`, `docs/g1-signoff.md`, `README.md`

## 9. ขอบเขตที่ห้ามขยาย

- ไม่เรียก TikTok จริง ไม่ login ไม่อ่าน/export credentials หรือ cookie
- `G0_VERIFIED` ยังเป็น `false` · ไม่เติม observed data dictionary จากการเดาหรือจาก source ของ package อื่น
- ไม่สร้าง live adapter, permission flow, Flow B/C, Warehouse หรือ bridge
- ไม่เพิ่ม permission ใน manifest
- ไม่แตะ browser profile หรือฐานข้อมูลจริงของผู้ใช้ — E2E ใช้ temp dir ที่สร้างเองเท่านั้น
- ไม่ publish/deploy/แก้ข้อมูลภายนอก
- ไม่เพิ่ม test ซ้ำ และไม่ refactor ใหญ่ที่ไม่ได้แก้ช่องว่างที่พบ
- coverage gate ของ 7 ไฟล์เดิมต้องยังผ่าน — branch ใหม่ต้องมี test จริง **ห้ามลด threshold**

## 10. ความเสี่ยงและทางถอย

| ความเสี่ยง | ทางจัดการ |
|---|---|
| หยุด service worker จาก Playwright ไม่ได้ | spike ก่อน (§4) ถ้าไม่ได้ → LC03 ระดับ browser = BLOCKED พร้อมเหตุผล คงหลักฐาน unit ไว้แต่ relabel ว่าเป็น simulation |
| ลดคาบ poll แล้วยังเกิน 1 s | หาสาเหตุจริง (IPC, IDB count, การ render) แล้วแก้ — ห้ามขยายงบ ถ้าสุดท้ายแก้ไม่ได้ให้บันทึก **FAIL** พร้อมค่าที่วัดได้ |
| เลขเปล่าใน mock ทำ unit test เดิมพัง | คงแถวแรกเป็น string เดิม และรันชุดเต็มก่อน commit |

| การเปลี่ยน `run.status`/`run.start` ทำ LC01 อ่อนลง | registry เป็นตัวเดียวทั้ง extension — เพิ่ม test ยืนยันว่าแท็บที่สองยังถูกปฏิเสธ |

## 11. Definition of done

- ทุก WP มี test ที่**รันจริง**แล้ว และบันทึกผลจริง (ค่า latency ที่วัดได้, จำนวน test, build hash, เวอร์ชัน browser)
- `npm run typecheck` · `npx vitest run` · `npm run test:coverage` · `npm run test:e2e` รันครบและรายงานผลตามจริง
- defect ที่พบมี regression test ที่จับ defect นั้นได้ก่อนแก้ (เมื่อทำได้)
- เอกสาร 4 ไฟล์สอดคล้องกันข้ามไฟล์ และไม่มีสถานะนอก §16.1
- รายการที่ติดข้อจำกัดถูกแยกออกมาเป็น blocker พร้อมเหตุผลที่พิสูจน์แล้ว ไม่ใช่การเดา
- **ไม่มีการอ้าง live-ready** ทุกกรณี — G0 ยังไม่ผ่าน

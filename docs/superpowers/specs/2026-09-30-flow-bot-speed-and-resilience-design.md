## ที่มา (2026-09-30)

รันระบบ Render จริงครั้งแรก ผู้ใช้รอเป็นชั่วโมงแล้วได้คลิป 0 ตัว สาเหตุที่ไล่จากหลักฐานจริง:

| สาเหตุ | หลักฐาน |
|---|---|
| **จังหวะพักของบอทเข้มเกินจำเป็น** — พักระหว่างสินค้า 2-6 นาที + พักยาว 15-40 นาทีทุก 4-6 สินค้า | ค่าตั้งวันแรก (6 ก.ย.) ตอนยังไม่รู้ว่า Google จับไวแค่ไหน · ใช้มา ~4 สัปดาห์ 51 งาน **ไม่เคยเจอสัญญาณโดนจับเลย** (captcha/403 = 0 ในหลักฐานทั้ง 10 ครั้ง) |
| **โหลดคลิปผ่านเมนูซ้อน 3 ชั้นพัง** (⋯ → Download → 1080p) | 2 รอบที่ลอง: Flow เรนเดอร์เสร็จใน ~1 นาทีทั้งคู่ แต่ขั้นโหลดพังทั้งคู่ (เมาส์เส้นโค้งปิดเมนูย่อย / หน้าต่างถูกปิด) |
| Gemini ล้ม 1 ครั้งแล้วพรอมต์ค้าง | แก้แล้ว (retry + ปุ่ม "สร้างพรอมต์ตอนนี้") |
| ถ้าโดนแบน ตอบไม่ได้ว่าเพราะอะไร | `flow-worker.log` เป็นข้อความ นับความถี่ย้อนหลังไม่ได้ ไม่เก็บ HTTP ที่ Google ตอบไม่ใช่ 200 |

ผู้ใช้ตัดสินใจ: ใช้ Flow ต่อ (ไม่ใช้ API) · **เร่งเต็มที่บนบัญชีสำรอง** ยอมรับว่าถ้าโดนจับก็สร้างบัญชีใหม่ · ต้องการอัตโนมัติ
ไม่ใช่ทำเอง · ต้องมีข้อมูลพอจะรู้ว่า "โดนเพราะอะไร"

## ขอบเขต — 3 ส่วน ทำเป็นลำดับ

### ส่วน 1: เร่งบอท (แก้ config + กติกาพัก)

**ค่าใหม่ใน `flow-worker.config.json`** (เปลี่ยนได้โดยไม่ build):

| ค่า | เดิม | ใหม่ | เหตุผล |
|---|---|---|---|
| `betweenProductsMs` | 2-6 นาที | **30-90 วิ** | AI4Next (ใช้จริงในตลาด) พัก 6-12 วิ; เราเอาช้ากว่า 5 เท่ายังเร็วกว่าเดิม 4 เท่า |
| `betweenBatchesMs` | 20-60 วิ | **10-30 วิ** | |
| `longBreakEvery` | ทุก 4-6 สินค้า | **ทุก 12-16 สินค้า** | |
| `longBreakMs` | 15-40 นาที | **5-10 นาที** | |
| `dailyBatchCap` | 24 ชุด (12 สินค้า) | **60 ชุด (30 สินค้า)** | ผู้ใช้เพิ่มสินค้า 5-10 ตัว/วัน ต้องไม่ชนเพดาน |
| `videoDailyCap` | 10 | **20** | เครดิต 1,000 = 66 คลิป; 20/วัน = 300 เครดิต |

**กติกาใหม่: พักตามความจริง ไม่ใช่ตามตาราง** — ถ้าคิวว่าง (ไม่มีงานรอ) ให้ **รีเซ็ต** ตัวนับพักยาว (`sessionStreak`) เพราะการที่คิวว่าง
ก็คือการพักอยู่แล้ว ปัจจุบันบอทนับสินค้าสะสมข้ามช่วงว่าง ทำให้ผู้ใช้เพิ่มสินค้าตัวที่ 5 ตอนบ่าย แล้วเจอพักยาวทันทีทั้งที่บอทว่างมา
ทั้งเช้า · กติกา: ว่าง ≥ `longBreakMs` ต่ำสุด = ถือว่าพักยาวไปแล้ว `sessionStreak = 0`

**ไม่แตะ**: ความหน่วงระดับคลิก/พิมพ์ (`actionDelayMs`, `typeCharDelayMs`, เส้นโค้งเมาส์) — พวกนี้คือสิ่งที่ทำให้ "คลิกเหมือนคน"
ไม่ใช่ตัวถ่วงเวลาหลัก และการเร่งตรงนี้ได้ประโยชน์น้อยแต่เสี่ยงมาก

**ผลที่คาด**: สินค้า 1 ตัว (รูป 2 รอบ + คลิป) จากเดิม ~25-70 นาทีรวมพัก → **~8-12 นาที** ถ้าคิวไม่ติดพักยาว

### ส่วน 2: โหลดคลิปแบบทน (ทาง B — ลิงก์ตรง)

**ข้อเท็จจริงที่พิสูจน์แล้ว (2026-09-30 จาก page.html ของหลักฐานจริง + curl):**
- เมื่อเมาส์วางบน `<flow-video-tile>` Flow ใส่ `<video src="https://flow-content.google/video/<uuid>?Expires=…&KeyName=labs-flow-prod-cdn-key&Signature=…">`
- ลิงก์นี้ **ดึงได้ตรงๆ โดยไม่ต้อง cookie** (curl ไม่ล็อกอิน → 200 video/mp4 3.4 MB, header `ftypisom`) หมดอายุ ~6 ชม. หลังออก
- ได้ **720p ต้นฉบับ** (ตัวเดียวกับเมนู "720p Original size") — 1080p upscale ไม่มีลิงก์ตรง ต้องผ่านเมนู

**ขั้นตอนใหม่ของ `download-preview`:**
1. hover ช่องคลิป (ทำอยู่แล้ว) → รอ `<video src^="https://flow-content.google/video/">` ปรากฏในช่องนั้น (≤ 10 วิ)
2. `page.request.get(src)` ด้วย context ของบอท (แนบ cookie ให้อยู่แล้ว เผื่อวันหน้า Google บังคับ) → ตรวจ `ftyp` → บันทึก
3. **ไม่แตะเมนู ⋯ เลย** ในขั้นนี้
4. ถ้าไม่เจอ `<video>` ใน 10 วิ → ถอยไปวิธีเมนู (โค้ดปัจจุบันที่แก้เรื่องเมาส์แล้ว) 1 ครั้ง
5. ถ้าทั้งสองไม่ได้ → สถานะใหม่ **`review_r3_manual`** = "คลิปเสร็จแล้วใน Flow แต่โหลดมาไม่ได้" ไม่ใช่ `failed` และ**ไม่หยุดคิว**
   (เครดิตจ่ายแล้ว คลิปมีจริง ปล่อยให้ผู้ใช้ไปโหลดเอง) — หน้าคิว Flow โชว์ลิงก์โปรเจกต์ + "ลองโหลดอีกครั้ง"

**1080p:** ขั้น `queued_upscale` (หลังกด "ผ่าน") ยังใช้เมนูเหมือนเดิม (เป็นทางเดียวที่ได้ upscale) แต่เปลี่ยนวิธีคลิกเมนูย่อย
เป็น**คีย์บอร์ด**: เปิดเมนู ⋯ ด้วยคลิก → `ArrowDown` จนถึง Download → `ArrowRight` เปิดเมนูย่อย → `ArrowDown` ถึง 1080p → `Enter`
(Angular Material menu รองรับ keyboard navigation มาตรฐาน — ไม่มีเรื่องเมาส์หลุดออกนอกเมนู) · พังก็ไม่เป็นไร: ผู้ใช้มี 720p อยู่แล้ว
งานเป็น `done` พร้อมหมายเหตุ "ได้ 720p (1080p โหลดไม่ได้)" **ไม่หยุดคิว**

**หลักการรวม**: ขั้นหลังจาก Flow เรนเดอร์เสร็จแล้ว **ห้ามทำให้งานเป็น failed/หยุดคิว** อีกต่อไป — สิ่งที่มีค่า (เครดิต+คลิป) ได้มาแล้ว

### ส่วน 3: สมุดบันทึกการกระทำของบอท (`FlowActivity`)

**เป้าหมาย**: ถ้าบัญชีโดนจับ ตอบได้ภายใน 1 นาทีว่า "ก่อนโดน บอทยิงกี่ครั้งใน 10 นาที / 1 ชม. / วันนั้น มีสัญญาณเตือนก่อนไหม
และตอนนั้นตั้งค่าอะไร" เพื่อตั้งบัญชีใหม่ให้อยู่ใต้เส้นนั้น

**ตาราง `FlowActivity`** — 1 แถวต่อ 1 สิ่งที่ Google เห็น:

| ฟิลด์ | ค่า |
|---|---|
| `at` | เวลา |
| `kind` | `generate_image` · `generate_video` · `upload` · `new_project` · `download` · `http_warn` (Google ตอบ 429/403/5xx โดยที่งานยังไม่พัง) · `bot_signal` (captcha / unusual activity / login หลุด) · `break` (พักจริง กี่ ms) · `session_start` |
| `jobId`, `round` | งานไหน |
| `detail` | JSON สั้นๆ: HTTP status, ข้อความสัญญาณ, ms ที่พัก |
| `configSnapshot` | ค่าจังหวะที่ใช้ตอนนั้น (5 ค่าจากส่วน 1) — เก็บเฉพาะแถว `session_start` |

**ไม่เก็บ**: คลิก/เมาส์/พิมพ์รายตัว (ปริมาณมหาศาล และ Google ดูจากคำขอกับพฤติกรรมรวม ไม่ใช่ตำแหน่งเมาส์)

**ที่เขียน**: `worker/activity.ts` ฟังก์ชันเดียว `logActivity()` fire-and-forget ห้าม throw (ห้ามทำให้งานพังเพราะ log) · เรียกจาก
`flow-driver.ts` ที่ click-generate / upload / new project / download และจาก `onResponse` เมื่อ status ≠ 2xx · จาก `index.ts`
ตอนพักและตอนเปิดบอท

**หน้าดู**: แถบสถานะบนหน้าคิว Flow เพิ่ม "วันนี้ยิง N ครั้ง · ถี่สุด X/10 นาที · สัญญาณเตือน: ไม่มี/ล่าสุด hh:mm" ·
สคริปต์ `scripts/flow-activity-report.mjs <วัน>` พิมพ์ตารางความถี่ต่อ 10 นาทีของวันนั้น (ใช้ตอนวิเคราะห์หลังโดน)

**เก็บนานแค่ไหน**: ตลอด (ไม่กี่ร้อยแถว/วัน)

## ไม่ทำในรอบนี้

- ย้ายเป็น extension — ข้อดีเดียวคือใช้โปรไฟล์จริง แต่ปัญหาที่เจอไม่ได้มาจากตรงนั้น (AI4Next ก็คลิก DOM เหมือนเรา)
- ใช้ API — ผู้ใช้ตัด
- เปลี่ยนวิธีคลิก/พิมพ์ระดับล่าง — ไม่ใช่ตัวถ่วง

## เกณฑ์สำเร็จ

1. สินค้า 1 ตัวจากเลือกรูปรอบ 2 → คลิป 720p อยู่ใน Angle ภายใน **15 นาที** เมื่อคิวว่าง (วัดจาก `FlowActivity`)
2. คลิปที่ Flow เรนเดอร์สำเร็จ **ไม่มีทางกลายเป็น failed** — อย่างแย่สุดคือ `review_r3_manual`
3. `node scripts/flow-activity-report.mjs 2026-10-01` ตอบความถี่ต่อ 10 นาทีได้

## ความเสี่ยงที่รับไว้

- เร่งแล้วอาจโดนจับ — บัญชีสำรองมีไว้เพื่อสิ่งนี้ และส่วน 3 ทำให้การโดนครั้งแรกกลายเป็นข้อมูล ไม่ใช่แค่ความเสียหาย
- ลิงก์ `flow-content.google/video/` อาจเปลี่ยนกติกา (บังคับ cookie/ตัดสิทธิ์) — มีทางถอย 2 ชั้น (เมนู → manual)

# รื้อแผง "ควรทำอะไรต่อ" ให้เป็นงานรายรอบที่เชื่อถือได้ทางสถิติ

วันที่: 2026-08-08 · สถานะ: อนุมัติแล้ว รอทำแผนลงมือ

## 1. ปัญหาที่แก้

ผู้ใช้รายงาน 4 อาการในหน้ารายได้ (`/dashboard`):

1. **แผง "ควรทำอะไรต่อ" ยาวมาก** ต้องเลื่อนผ่านไปนานกว่าจะถึงตัวเลขรายได้
2. **ไม่รู้ว่าคำแนะนำที่เห็นเป็นของช่วงไหน** ทับกับสัปดาห์ก่อนหรือคำนวณใหม่ทุกครั้ง — อยากให้เป็น "งานที่ควรทำ" มีกรอบเวลาและ deadline
3. อยากให้มากกว่า rule-based — พิจารณาใช้ Gemini ช่วยวิเคราะห์
4. **แผงนำเข้าข้อมูลไม่บอกว่ารอบถัดไปควรลงวันไหน** (ควรเป็น 5-7 วันหลังรอบล่าสุด)

ระหว่าง brainstorm ผู้ใช้ถามเพิ่มว่ากฎ rule-based ที่ใช้อยู่คืออะไรและเชื่อได้แค่ไหน มีการเรียนรู้ไหม — คำถามนี้นำไปสู่การวัดจริงซึ่งเปลี่ยนขอบเขตของงานอย่างมีนัยสำคัญ (หัวข้อ 4)

## 2. ขอบเขต

โปรเจกต์นี้คือก้อน **C** ก้อนสุดท้ายจาก 3 ก้อน (A → B → C):

- **A (merge แล้ว)** — ธีม Navy + Brass, ตัวอักษร, กฎ affordance
- **B (merge แล้ว)** — รื้อหน้ารายการสินค้า
- **C (สเปกนี้)** — รื้อแผง "ควรทำอะไรต่อ" ในหน้ารายได้

**ไม่ทำในสเปกนี้:** ไม่แตะการนำเข้าข้อมูล (parser, Server Action) · ไม่แตะ schema · ไม่แตะกราฟรายได้/ตารางราย-คลิป/reconciliation · ไม่ใช้ Gemini (ดูหัวข้อ 3 ข้อ 3)

## 3. การตัดสินใจที่ล็อกแล้ว

| # | ประเด็น | ที่เลือก |
|---|---|---|
| 1 | สัญญาณที่ตัดออก | ตัด `reach-no-convert` และ `fading` — เก็บเฉพาะสัญญาณเชิงบวกที่บอกว่า "ควรทำอะไร" ไม่ใช่ "อะไรตายแล้ว" |
| 2 | กรอบเวลา | รอบ 7 วันแบบเลื่อนได้ (rolling) ยึดตามรอบนำเข้าข้อมูลล่าสุด ไม่ใช่สัปดาห์ปฏิทิน — เพราะผู้ใช้นำเข้าข้อมูลตามจังหวะตัวเอง ไม่ตรงปฏิทิน |
| 3 | Gemini | **ไม่ใช้** — ปัญหาทั้ง 4 ข้อไม่มีข้อไหนต้องพึ่ง AI และการเก็บผลลัพธ์ AI ให้นิ่งทั้งรอบต้องเพิ่มตารางใน schema + latency + failure mode ใหม่ ไม่คุ้มกับสิ่งที่ได้ (สำนวนลื่นขึ้นเล็กน้อย) |
| 4 | รอบนำเข้าถัดไป | แสดงทั้งวันที่และนับถอยหลัง (`แนะนำรอบหน้า 15 ส.ค. (อีก 7 วัน)`) ใช้ค่าเดียวไม่ใช่ช่วง โดยใช้ `IMPORT_STALE_DAYS = 7` ที่มีอยู่แล้ว ไม่สร้างค่าคงที่ใหม่ |
| 5 | ความน่าเชื่อถือของเกณฑ์ | แทนค่าคงที่ที่ตั้งเองด้วยการทดสอบทางสถิติ (ดูหัวข้อ 4) |

## 4. รื้อเกณฑ์สัญญาณ — ส่วนที่สำคัญที่สุดของงานนี้

### 4.1 ที่มา: วัดแล้วพบว่าเกณฑ์ปัจจุบันเชื่อไม่ได้

`lib/recommender.ts` ไม่มีการเรียนรู้ใดๆ ค่าทั้งหมดถูกพิมพ์ไว้ตอนช่องยังเล็กแล้วแช่ไว้ (`MIN_VIEWS_FOR_CONV = 500`, `MIN_ORDERS_FOR_CONV = 2`, อัตราส่วน `0.8` และ `1.3`)

วัดช่วงความเชื่อมั่น (Wilson 95%) ของ conversion rate ต่อคลิปที่ยิงสัญญาณจริง เทียบกับค่าเฉลี่ยช่อง (`channelConv = 0.2148%` = 1 ออเดอร์ต่อ 466 วิว):

| คลิป | วิว / ออเดอร์ | อ้างว่า | ช่วงจริง 95% | ผล |
|---|---|---|---|---|
| ชั้นวางของ 5 ชั้น | 29,489 / 83 | กำลังมา | 1.06–1.62 เท่า | เชื่อได้ |
| รถเข็นตู้เก็บเครื่องสำอาง | 14,118 / 26 | กำลังมา | 0.59–1.26 เท่า | **คร่อม 1.0 แยกไม่ออก** |
| กระปุกกรองน้ำมัน | 1,038 / 3 | ของดีคนไม่เห็น | 0.46–3.94 เท่า | **กว้างจนไร้ความหมาย** |

**2 ใน 3 สัญญาณที่จะเหลือ แยกจาก "ธรรมดา" ไม่ได้ทางสถิติ**

รากของปัญหาคือ `MIN_ORDERS_FOR_CONV = 2` ต่ำเกินไปมาก — คำนวณว่าต้องมีออเดอร์กี่ตัวบนคลิปเดียวถึงจะพิสูจน์ได้ว่า conv สูงกว่าช่อง 1.3 เท่า (เกณฑ์ของ `hidden-gem`):

| ออเดอร์บนคลิปนั้น | ช่วงที่วัดได้ | แยกออกจากธรรมดาได้ไหม |
|---|---|---|
| 2 (เกณฑ์ปัจจุบัน) | 0.36–4.72 เท่า | ไม่ได้ |
| 10 | 0.71–2.39 เท่า | ไม่ได้ |
| 50 | 0.99–1.71 เท่า | เฉียดฉิว |

ทั้งช่องมีคลิปเดียวที่มีออเดอร์ถึงระดับนั้น

### 4.2 ค้นพบเพิ่ม: เงื่อนไข "วิวต้องน้อย" กำลังปิดบังคลิปที่ conv ดีที่สุด

จำลองกฎที่ใช้ CI แทนอัตราส่วนตายตัว โดยไม่บังคับว่าวิวต้องน้อยกว่าค่ากลาง พบคลิปที่กฎปัจจุบันมองไม่เห็นเลย:

```
โต๊ะรีดผ้ายืนรีด ปรับได้ 3 ระดับ และ 4 ระดับ รุ่นออริจินอล
วิว 3,590 · 21 ออเดอร์ · ขอบล่างของช่วงเชื่อมั่น = 1.78 เท่าของช่อง
```

**นี่คือคลิปที่ conv พิสูจน์ได้แน่นที่สุดในช่อง** (แน่นกว่าชั้นวางของที่ได้ 1.06 เท่า) แต่ไม่เคยโผล่ในแผง เพราะ:
- `hidden-gem` บังคับ `views < medianViews` (1,090) — คลิปนี้มี 3,590 จึงถูกตัด
- `emerging` บังคับว่าวิวต้องกำลังพุ่ง — คลิปนี้โตช้าแล้ว จึงตกอีก
- หล่นผ่านทั้ง 4 กฎ = มองไม่เห็น

เจตนาเดิมของเงื่อนไข "วิวน้อย" คือ *"ของดีที่คนยังไม่เห็น ควรดันต่อ"* แต่ผลข้างเคียงคือมันตัดสินค้าที่พิสูจน์แล้วว่าขายดีจริงทิ้งด้วย ทั้งที่นั่นคือคำตอบตรงที่สุดของคำถาม "ควรทำคลิปซ้ำให้ตัวไหน"

### 4.3 ชุดสัญญาณใหม่ — เหลือ 2 แบบ เรียกชื่อตามสิ่งที่วัดได้จริง

| สัญญาณ | เกณฑ์ | อ้างอะไร | เชื่อได้เพราะ |
|---|---|---|---|
| **กำลังโต** | `viewDelta >= medianViews` | "คลิปนี้วิวกำลังพุ่ง" — **ไม่อ้างเรื่องยอดขายเลย** | วิวเป็นเลขหลักพัน-หมื่น เห็นชัดโดยไม่ต้องพึ่งสถิติละเอียด |
| **ขายดีจริง** | `wilsonLowerBound(orders, views) > channelConv` | "สินค้านี้ conv ดีกว่าค่าเฉลี่ยของช่องจริง" | ผ่านการทดสอบทางสถิติ เงียบเองเมื่อ n ไม่พอ |

ทั้งสองยังผ่านตัวกรองคุณภาพเดิม `badRatio < MAX_BAD_RATIO` ก่อน

**คลิปเดียวติดได้ทั้งสองป้าย** — แสดงป้ายทั้งคู่บนแถวเดียวกัน ไม่ใช่ "เจอกฎแรกแล้วหยุด" แบบเดิม

### 4.4 ค่าคงที่ที่ถูกลบ และผลที่ตามมา

| เดิม | ใหม่ |
|---|---|
| `MIN_VIEWS_FOR_CONV = 500` | **ลบ** — CI ทำหน้าที่นี้เอง (วิวน้อย = ช่วงกว้าง = ไม่ผ่าน) |
| `MIN_ORDERS_FOR_CONV = 2` | **ลบ** — เหตุผลเดียวกัน |
| `conv >= channelConv * 1.3` | **ลบ** — แทนด้วยการทดสอบทางสถิติ |
| `conv >= channelConv * 0.8` (ใน emerging) | **ลบ** — วัดแล้วพบว่าไม่กรองอะไรจริง (0.8 เท่าคือต่ำกว่าค่าเฉลี่ย) |
| `GUARD_STALE_FACTOR` + `checkGuardHealth` | **ลบทั้งฟังก์ชัน** — มันมีไว้เฝ้า `MIN_VIEWS_FOR_CONV` ที่ถูกลบไปแล้ว |
| `MAX_BAD_RATIO = 0.3` | **เก็บ** — ตัวกรองคุณภาพข้อมูล เป็นสัดส่วน ไม่ผูกกับสเกลช่อง |
| `medianViews`, `channelConv` | **เก็บ** — คำนวณจากข้อมูลอยู่แล้ว ปรับตัวเอง |

หลังแก้ ระบบเหลือค่าที่ตั้งด้วยมือแค่ตัวเดียว (`MAX_BAD_RATIO`) ที่เหลือคำนวณจากข้อมูลเองทั้งหมด และมีการทดสอบทางสถิติเป็นด่านสุดท้าย

### 4.5 ผลที่คาดไว้กับข้อมูลปัจจุบัน (ใช้เป็นเกณฑ์ตรวจรับ)

จำลองแล้วด้วยข้อมูลจริง:

| สัญญาณ | คลิปที่ยิง |
|---|---|
| กำลังโต | ชั้นวางของ 5 ชั้น (+1,326 วิว) · รถเข็นตู้เก็บเครื่องสำอาง (+1,269 วิว) |
| ขายดีจริง | ชั้นวางของ 5 ชั้น (1.06 เท่า) · โต๊ะรีดผ้ายืนรีด (1.78 เท่า) |
| **กระปุกกรองน้ำมัน** | **ต้องเงียบ** (3 ออเดอร์ ยังพิสูจน์ไม่ได้) |

## 5. หน้าตาแผง

### 5.1 หัวแผง

```
งานรอบนี้                                          2 งาน
คำนวณจากข้อมูลวิวถึง 3 ส.ค. · รายได้ถึง 2 ส.ค.
ทำก่อนนำเข้ารอบหน้า — 10 ส.ค. (อีก 2 วัน)
```

- ชื่อเปลี่ยนจาก "ควรทำอะไรต่อ" เป็น **"งานรอบนี้"** — บอกว่าเป็นชุดงานที่มีขอบเขต ไม่ใช่คำแนะนำลอยๆ ที่สะสมทับกัน
- **บรรทัดกลางแยกความสดของข้อมูลตามชนิด** เพราะสัญญาณใช้ทั้งวิวและรายได้ ถ้าอันใดอันหนึ่งเก่า ผลก็เก่าตามตัวที่เก่ากว่า — ไม่ยุบเป็นวันเดียวเพราะจะซ่อนว่าอันไหนล้าหลัง
- **Deadline** = `นำเข้าล่าสุดของชนิดที่เก่าที่สุด + IMPORT_STALE_DAYS` คือวันที่ลิสต์จะถูกคำนวณใหม่
- ตอบคำถาม "ทับกับสัปดาห์ก่อนไหม" ตรงๆ: ไม่ทับ ทุกครั้งที่นำเข้าข้อมูล ลิสต์คำนวณใหม่ทั้งชุด ไม่มีการสะสม

### 5.2 แถวงาน

```
[กำลังโต] [ขายดีจริง]  ชั้นวางของ 5 ชั้น
ทำ angle ใหม่ซ้ำ
วิวเพิ่ม 1,326 ในรอบล่าสุด (รวม 29,489) · 83 ออเดอร์ · conv 1.06–1.62 เท่าของช่อง
ทำซ้ำไปแล้ว 2 คลิป · ลงล่าสุด 6 ส.ค.
```

- **ป้ายซ้อนได้** — คลิปที่ทั้งโตและขายดีคือของที่ควรทำซ้ำที่สุด ต้องเห็นว่าเด่นกว่าตัวอื่น
- **โชว์ช่วงแทนตัวเลขเดียว** (`1.06–1.62 เท่า` ไม่ใช่ `1.31 เท่า`) — ตัวเลขเดียวสร้างความมั่นใจเกินจริง ช่วงบอกความไม่แน่นอนไปในตัว
- **บรรทัด "ทำซ้ำไปแล้ว N คลิป" เก็บไว้เหมือนเดิม** — ตรวจจากสายเลือด `duplicatedFromId` ไม่ใช่ให้ติ๊กเอง (ของที่ต้องจำไปติ๊กคือของที่ลืมได้อีกอย่าง)
- กดแถวแล้วเปิด entry นั้น (`onOpenEntry`) เหมือนเดิม

### 5.3 สถานะว่าง

```
งานรอบนี้ · ไม่มีอะไรต้องรีบ
รอบนี้ไม่มีคลิปที่เข้าเกณฑ์ — ลงคลิปใหม่ต่อได้ตามปกติ
(ตรวจ 36 คลิปที่มีข้อมูลครบ)
```

ข้อความเดิม (*"ยังไม่มีสัญญาณที่ชัดพอจะแนะนำ — นำเข้าข้อมูลให้ครบก่อน"*) อ่านเหมือนระบบทำงานไม่ได้ ทั้งที่คำตอบคือ "ไม่มีอะไรเด่น" ซึ่งจะเป็นสภาวะปกติบ่อยขึ้นหลังใส่ CI-gating · วงเล็บท้ายบอกว่าระบบทำงานจริง ไม่ได้นิ่งเพราะพัง

### 5.4 บรรทัดสถานะข้อมูลท้ายแผง

| บรรทัด | ทำอย่างไร |
|---|---|
| `ยังไม่มีข้อมูลวิว N คลิป` | **เก็บ** — ตอนนี้ N = 59 เป็นข้อจำกัดจริงที่ต้องเห็น |
| `สัญญาณความเคลื่อนไหวจะใช้ได้หลังนำเข้ารอบที่ 2` | **เก็บ** |
| คำเตือนจาก `checkGuardHealth` | **ลบ** พร้อมฟังก์ชัน (หัวข้อ 4.4) |

## 6. รอบนำเข้าถัดไป

เพิ่มบรรทัดในแผง "อัปล่าสุด" (`ImportLogPanel`):

```
อัปล่าสุด
  รายได้    8 ส.ค. 14:20 · 361 ออเดอร์ · 26 พ.ค.–2 ส.ค.
            แนะนำรอบหน้า 15 ส.ค. (อีก 7 วัน)
  วิวคลิป   3 ส.ค. · 3 จาก 3 ไฟล์

```

เมื่อเลยกำหนดแล้ว ใช้ข้อความเตือนเดิมที่มีอยู่ (`— เกินกำหนดมา N วัน`) ไม่แสดงซ้อนสองข้อความ

**ข้อควรระวังที่ตรวจพบ:** ปัจจุบัน `ImportLog` **ยังไม่มีแถวของ `orders` เลย** (รอบนำเข้ารายได้ครั้งล่าสุดเกิดก่อนฟีเจอร์ log จะถูกเพิ่ม — ไม่ใช่บั๊ก) แต่ `ImportLogPanel` วนแสดงจากแถว log เท่านั้น บรรทัดรายได้จึงหายไปทั้งบรรทัด — **บรรทัด "แนะนำรอบหน้า" ต้องคำนวณจาก `reminder.daysSinceOrdersImport`/`daysSinceMetricsImport` ซึ่งอ่านจากตัวข้อมูลเอง (`AffiliateOrder.importedAt` / `ClipMetric.importedAt`) ไม่ใช่จาก log** เพื่อให้แสดงได้แม้ยังไม่มีแถว log

## 9. งานถัดไปที่ตกลงกันไว้ (ไม่อยู่ในสเปกนี้)

ผู้ใช้จะ **นำเข้าข้อมูลรอบใหม่หลังงานนี้เสร็จ** เพื่อตรวจว่าเกณฑ์ที่ปรับตัวเองทำงานถูกกับข้อมูลที่ขยับจริง แล้วค่อยพิจารณาโปรเจกต์ถัดไป:

**โปรเจกต์ D (ยังไม่เริ่ม): Thompson Sampling / multi-armed bandit** — คำถาม "ควรทำคลิปซ้ำให้สินค้าตัวไหน" คือปัญหา multi-armed bandit ตรงตัว (สินค้า = แขน, ทำคลิป = ดึงแขน, ออเดอร์ = รางวัล) Thompson Sampling เก็บการกระจายความน่าจะเป็นทั้งก้อนแทนตัวเลขเดียว จึงทำงานได้ดีกับ n น้อยเพราะมันแสดงความไม่แน่นอนออกมาแทนที่จะซ่อน และแก้ปัญหาที่ระบบปัจจุบันไม่แตะเลยคือความสมดุลระหว่าง "ทำซ้ำของที่รู้ว่าเวิร์ค" กับ "ลองของใหม่"

ต้องออกแบบใหม่ตั้งแต่นิยามรางวัล (ออเดอร์? เงิน? ปัง/ไม่ปัง?) และวิธีนำเสนอความน่าจะเป็นที่ไม่ทำให้เชื่อเกินจริง จึงเป็นคนละโปรเจกต์

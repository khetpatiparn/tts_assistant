# List Page UX Polish

**วันที่:** 2026-07-29
**สถานะ:** อนุมัติแล้ว รอเขียน implementation plan

## 1. บริบท

หลัง merge `feature/route-split-and-list-page` ผู้ใช้ทดลองใช้จริงแล้วให้ feedback 3 ข้อ:

1. อยู่ในหน้า `/entry/[id]` แล้วไม่รู้จะกลับไปหน้ารายการยังไง — ต้องเลื่อนลงไปหาลิงก์ "ดูทั้งหมด" ท้ายแถบข้าง
2. หน้ารายการ (`/`) ดูโล่ง มีแค่รูป+ชื่อ วันที่ตัวเล็กเกินไป อยากเห็นข้อมูลยอดขายด้วย
3. อยากกรองรายการตามช่วงวันที่ได้

## 2. ข้อ 1 — ปุ่มย้อนกลับ

`ClapperHeader` (`components/clapper-header.tsx`) ใช้เฉพาะในหน้า entry เท่านั้น (`components/entry-workspace.tsx`) — หน้าอื่น (`/`, `/dashboard`, `/core-prompt`) ใช้ `AppHeader` ที่มี nav อยู่แล้ว เพราะบริบทนี้คงที่ (ClapperHeader ไม่มีที่ใช้อื่น) จึงใส่ลิงก์ "← กลับไปรายการ" แบบถาวรไว้เหนือโลโก้ ไม่ต้องเพิ่ม prop

## 3. ข้อ 2 — ยอดขาย + ยอดวิวในแถวรายการ

### 3.1 กฎการโชว์ยอดขาย (สำคัญ — ต้องแยกจาก `summarizeEntryOutcome` เดิม)

`lib/angle.ts` มี `summarizeEntryOutcome()` อยู่แล้ว (ใช้ในแผง angle) แต่มันรวม `finalRevenue` แบบไม่แยกสถานะออเดอร์ ("จ่ายแล้ว"/"รอ" ปนกัน) — เหมาะกับบริบทแผง angle ที่สนใจแค่ผลลัพธ์รวม แต่**ไม่พอสำหรับหน้ารายการ** ที่ผู้ใช้ต้องการเห็นชัดว่ายอดไหน "จ่ายแล้วจริง" กับยอดไหน "ยังรอรอบจ่าย" (เหตุผลเดียวกับที่หน้ารายการเดิมตัดคอลัมน์รายได้ออก — settlement lag ทำให้คลิปใหม่ดูเหมือนเจ๊ง)

`lib/dashboard.ts` มี `revenueByClip()` ที่แยกด้วยสถานะออเดอร์จริง (`PAID_STATUS`) อยู่แล้ว แต่ group ด้วย `contentId` (video id) ไม่ใช่ `entryId` — ใช้ตรงๆ ไม่ได้เพราะหน้ารายการ key ด้วย entry

**จึงต้องเขียนฟังก์ชันใหม่** ที่ group ด้วย `matchedEntryId` แบบเดียวกับ `revenueByClip` แต่คำนวณ **`finalRevenue`** (ไม่ใช่ `gmv`) แยกตามสถานะจ่าย — เพราะ "settled" ที่ผู้ใช้อยากเห็นคือเงินที่ได้จริง ไม่ใช่ยอดขายตั้งต้น (GMV ≠ เงินจริง ตามที่ CLAUDE.md ระบุไว้แล้ว)

ผลลัพธ์ต่อ entry:
```ts
type EntrySalesSummary = {
  settledRevenue: number;   // sum(finalRevenue) เฉพาะออเดอร์สถานะ PAID_STATUS
  pendingGmv: number;       // sum(gmv) ของออเดอร์ที่ยังไม่ settle และไม่ใช่ "ไม่มีสิทธิ์"
  orderCount: number;       // จำนวนออเดอร์ทั้งหมดที่ match กับ entry นี้ (ทุกสถานะ)
  views: number | null;     // จาก ClipMetric ล่าสุด (capturedOn มากสุด) ที่ match กับ entry นี้
};
```

### 3.2 กฎการแสดงผล

- `orderCount === 0` → ไม่โชว์บรรทัดยอดขายเลย (ไม่มีอะไรให้พูด ไม่ใช่ "฿0")
- `orderCount > 0` → โชว์ `฿<settledRevenue> · <orderCount> ออเดอร์`
- ถ้า `pendingGmv > 0` เพิ่มเติม → ต่อท้ายด้วย tag เล็ก **"รอรอบจ่าย"** (ไม่ใช่ตัวเลข ไม่ใช่ ฿pendingGmv — แค่บอกว่ามีของค้างอยู่ กันความสับสนแบบเดียวกับที่แดชบอร์ดทำ)
- `views !== null` → โชว์ `<views> วิว` แยกอีกบรรทัด/ตำแหน่ง ถ้า `views === null` (ไม่มี ClipMetric match เลย) ไม่โชว์อะไร

### 3.3 การคำนวณ — ฝั่ง server ทั้งหมด ไม่ query ซ้ำต่อแถว

หน้ารายการโหลด `AffiliateOrder` และ `ClipMetric` ทั้งตาราง (หลักร้อยแถวตอนนี้ — เทียบเท่าขนาดที่ `/dashboard` โหลดอยู่แล้วทุกวันนี้) มา group เป็น `Map<entryId, EntrySalesSummary>` **ครั้งเดียวต่อ request** แล้ว lookup ตาม 30 แถวที่แสดงในหน้านั้น **ไม่ส่งข้อมูลดิบของ order/metric ลง client** — ส่งแค่ 4 ตัวเลขต่อแถวที่คำนวณเสร็จแล้ว (สอดคล้องกับหลักการของ route-split ที่เพิ่งทำ: ไม่ส่งของหนักที่ไม่ได้ใช้)

### 3.4 การแสดงวันที่

`postedLabel`/`createdLabel` ที่มีอยู่ (`components/entry-list.tsx`) ยังใช้ตรรกะเดิม (UTC สำหรับ `postedAt`, local สำหรับ `createdAt`) แค่ขยาย class จาก `text-[0.6rem]` เป็น `text-xs` และจัดตำแหน่งให้เด่นขึ้น — **ห้ามเปลี่ยนตรรกะคำนวณวันที่**

## 4. ข้อ 3 — ตัวกรองช่วงวันที่

### 4.1 พารามิเตอร์ URL

เพิ่ม `?from=YYYY-MM-DD&to=YYYY-MM-DD` ต่อจาก `?q=`/`?status=`/`?page=` ที่มีอยู่ — ค่าใดค่าหนึ่งหรือทั้งคู่ก็กรองได้ (`from` อย่างเดียว = "ตั้งแต่วันที่นั้นเป็นต้นไป", `to` อย่างเดียว = "จนถึงวันที่นั้น")

### 4.2 กฎการกรอง

- กรองบน `postedAt` เทียบกับ **UTC date** (ตรงกับที่ `postedAt` เก็บเป็น UTC midnight อยู่แล้ว — พึ่งพฤติกรรมเดิมของฟิลด์นี้ ไม่ใช่ตรรกะใหม่)
- **entry ที่ `postedAt` เป็น `null` (ยังไม่ได้ลงคลิป) จะถูกซ่อนโดยอัตโนมัติทันทีที่มี `from` หรือ `to` ค่าใดค่าหนึ่งไม่ว่าง** — เพราะ "ยังไม่ได้ลงคลิป" ไม่มีวันที่ให้เทียบ การจะให้ "อยู่ในช่วงวันที่" กับ entry ที่ไม่มีวันที่เป็นเรื่องกำกวม จึงเลือกซ่อนแทนการเดา
- ใช้ร่วมกับค้นหา/กรองสถานะได้ปกติ (ทุกเงื่อนไข AND กัน) — ถ้าผู้ใช้กรองสถานะ "ยังไม่ได้ลงคลิป" พร้อมกับตั้งช่วงวันที่ ผลลัพธ์จะว่างเสมอ (ตรงไปตรงมาตามตรรกะข้อบน ไม่ต้องมี UI พิเศษเตือน)
- `matchCount`/`totalPages` นับ**หลังกรองครบทุกเงื่อนไข** (สถานะ + คำค้น + ช่วงวันที่)

### 4.3 UI

ช่อง `<input type="date">` สองช่อง (จาก/ถึง) เพิ่มในฟอร์มค้นหาเดิม (`components/entry-list.tsx`) — submit แบบ GET เหมือนช่องค้นหา ค่าปัจจุบันของ `status`/`page` ถูก carry ผ่าน hidden input เหมือนที่ `status` ทำอยู่แล้วตอนนี้

## 5. ไม่ทำ

- ไม่แก้ `lib/dashboard.ts` / `lib/angle.ts` เดิม — ฟังก์ชันใหม่ (ข้อ 3.1) แยกไฟล์หรือรวมใน `lib/entry-queries.ts`
- ไม่แก้ `lib/entry-rows.ts` / `lib/entry-search.ts` — ตรรกะค้นหา/จัดชั้น/แบ่งหน้าเดิมไม่เปลี่ยน ตัวกรองวันที่เป็นชั้นกรองเพิ่มก่อนเข้า `searchAndFilter`/`paginate`
- ไม่เรียงลำดับรายการใหม่ตามยอดขาย/ยอดวิว — ยังเรียงด้วย `sortEntriesForRail` เหมือนเดิม (ยอดขาย/วิวเป็นแค่ข้อมูลแสดงผล ไม่ใช่ตัวจัดลำดับ)
- ไม่เพิ่ม date-picker แบบ calendar UI (dropdown ปฏิทิน ฯลฯ) — ใช้ `<input type="date">` ของเบราว์เซอร์ตรงๆ

## 6. เกณฑ์ว่าสำเร็จ

1. หน้า entry มีปุ่ม/ลิงก์กลับหน้ารายการที่เห็นได้ทันทีโดยไม่ต้องเลื่อน
2. แถวในหน้ารายการที่มีออเดอร์แสดง `฿settledRevenue · N ออเดอร์` และ tag "รอรอบจ่าย" เมื่อมี `pendingGmv > 0` — แถวที่ไม่มีออเดอร์ไม่โชว์บรรทัดนี้เลย
3. แถวที่มี `ClipMetric` match แสดงจำนวนวิวล่าสุด
4. ตัวกรองช่วงวันที่ใช้งานได้ ผสานกับค้นหา/กรองสถานะ/แบ่งหน้าได้ถูกต้อง อยู่ใน URL (back/forward/refresh ใช้ได้เหมือนตัวกรองอื่น)
5. entry ที่ยังไม่ได้ลงคลิปหายจากผลลัพธ์ทันทีที่ตั้งช่วงวันที่ (ไม่ error ไม่ค้าง)
6. ไม่มีข้อมูล order/metric ดิบถูกส่งลง client — เฉพาะตัวเลขสรุปต่อแถว
7. วันที่ในแถวยังถูกต้อง (ไม่เพี้ยนวันจากการแก้ font size)

# แยก route ทั้งแอป + หน้ารายการ

**วันที่:** 2026-07-29
**สถานะ:** อนุมัติแล้ว รอเขียน implementation plan

## 1. ปัญหา

ผู้ใช้เริ่มจาก "แถบข้างหาของยาก อยากให้กว้างขึ้น ไม่อยากเห็น scrollbar อยากให้แบ่งหมวดหมู่ชัดเจน" แต่พอวัดข้อมูลจริงแล้วเจอว่าปัญหาที่แท้จริงอยู่คนละที่

### 1.1 การจัดกลุ่มตามเดือนให้กองใหญ่กองเดียว

| กลุ่ม | จำนวน |
|---|---|
| ก.ค. 2026 | 51 |
| มิ.ย. 2026 | 13 |
| ยังไม่ได้ลงคลิป | 9 |

70% อยู่ในกองเดียว การ "แบ่งกลุ่ม" จึงไม่ให้ความรู้สึกว่าแบ่ง และกองของเดือนปัจจุบันบวมขึ้นเรื่อยๆ ตลอดไป

การแบ่งตามสถานะงานแย่กว่า — ลงคลิปแล้ว 67 / รอลง 5 / ร่างเปล่า 1 (92% กองเดียว)

### 1.2 payload โตแบบไม่มีเพดาน (ปัญหาที่แท้จริง)

`app/page.tsx` ดึง `promptEntry.findMany()` ทุกแถวพร้อม `chatgptOutput` เต็ม แล้วส่งลงเบราว์เซอร์ทุกครั้งที่เปิดหน้า พร้อมกับ `AffiliateOrder` (269) `ClipMetric` (38) `FollowerActivity` (168) ทั้งหมด ไม่ว่าผู้ใช้จะเปิดแท็บไหน

วัดจาก `dev.db` จริง:

| ฟิลด์ | byte เฉลี่ย/แถว |
|---|---|
| `chatgptOutput` | 8,714 |
| `productInfo` | 2,067 |
| `productSpec` | 669 |
| ที่เหลือรวมกัน | ~950 |
| **รวม** | **12.4 KB** |

`chatgptOutput` กิน 70% ของ payload และ**แถบข้างไม่เคยใช้ฟิลด์นี้เลย**

คาดการณ์ตามเป้าการผลิตของผู้ใช้ (5-10 คลิป/วัน):

| | จำนวนแถว | payload/การเปิดหน้า |
|---|---|---|
| ตอนนี้ | 75 | 0.9 MB |
| 3 เดือน @5/วัน | 523 | 6.6 MB |
| 3 เดือน @10/วัน | 973 | 12.2 MB |
| 6 เดือน @10/วัน | 1,873 | **23.5 MB** |

**สาเหตุเชิงโครงสร้าง:** ทุกอย่างอยู่หน้าเดียวจึงต้องโหลดทุกอย่างเสมอ ไม่ใช่ผลข้างเคียงที่แก้ด้วยการ optimize query แต่เป็นผลโดยตรงของการไม่มี route

### 1.3 อัตราการผลิตกำลังจะโต 5-10 เท่า

คลิปต่อสัปดาห์ที่ผ่านมา: 3, 6, 5, 3, 23, 13, 11 — เป้าใหม่คือ 5-10 คลิป/วัน = **35-70 คลิป/สัปดาห์**

ดีไซน์ใดก็ตามที่กางรายการของ "สัปดาห์นี้" จะกลายเป็นกำแพง 70 แถว การแก้ด้วยการจัดกลุ่มให้ดีขึ้นจึงเป็นการเลื่อนปัญหา ไม่ใช่แก้ปัญหา

### 1.4 แถบข้างกว้าง 240px ทำงานนี้ไม่ได้ไม่ว่าจะออกแบบดีแค่ไหน

ความยาวชื่อสินค้า: กลาง 23 ตัวอักษร · 90% ที่ 38 · ยาวสุด 125 ต่อให้ขยายเป็น 320px ก็ยังใส่ได้แค่ชื่อกับวันที่ ไม่มีที่ให้ตัวกรอง ไม่มีที่ให้คอลัมน์สถานะ/angle

## 2. เป้าหมาย

1. หน้าไหนก็ตามต้องไม่โหลดข้อมูลที่โตตามจำนวนสะสมทั้งก้อน
2. หา entry เจอได้จริงที่ 1,000+ รายการ ด้วยตัวกรอง + ค้นหา + pagination
3. ยังสลับ entry ระหว่างทำงานได้เร็วโดยไม่ต้องย้อนกลับไปหน้ารายการทุกครั้ง
4. หน้าตาและประสิทธิภาพไม่เสื่อมลงตามเวลา — อีก 3 ปีต้องเหมือนเดิม

## 3. ไม่ใช่เป้าหมาย

- **หมวดหมู่สินค้า** (ครัว/แมว/จัดเก็บ) — ตรงกับคำที่ผู้ใช้พูดที่สุด แต่ต้องเพิ่มคอลัมน์ + ให้ AI เดา + UI แก้เอง + backfill 73 แถว ขนาดพอๆ กับฟีเจอร์ angle tracking ทั้งตัว และงานที่มันแก้ ระบบค้นหาแบบจัดชั้นที่มีอยู่แก้ไปแล้วเกือบหมด ดีไซน์นี้ไม่ขวางการเพิ่มทีหลัง (ที่ที่มันควรอยู่คือตัวกรองในหน้ารายการ)
- **ยุบสายเลือดทำซ้ำเป็นแถวเดียว** — วัดแล้วมี 4 ลูกจาก 75 แถว ประหยัดได้ 5% ยังไม่คุ้ม กลับมาพิจารณาเมื่อสินค้าหนึ่งมี 5-6 takes
- **virtualized list** — ไม่ใช่ปัญหาที่ 30 แถว/หน้า
- **แยก Brief กับ ผลลัพธ์ เป็นคนละ route** — ใช้ข้อมูลก้อนเดียวกัน แยกแล้วไม่ประหยัด payload แต่เสียความเร็วตอนสลับ
- **คอลัมน์รายได้ในหน้ารายการ** — ดูหัวข้อ 5.2
- **เปลี่ยน schema** — งานนี้ไม่แตะ `prisma/schema.prisma`

## 4. แผนที่ route

| Route | หน้าที่ | ข้อมูลที่โหลด |
|---|---|---|
| `/` | รายการ · ค้นหา · กรอง · pagination | แถวเบา 30 แถว/หน้า + จำนวนรวม |
| `/entry/[id]` | ทำงานกับ entry เดียว | entry นั้นเต็ม + สายเลือดแบบเบา + ล่าสุด 15 แถวเบา |
| `/entry/new` | สร้าง entry ใหม่ | ล่าสุด 15 แถวเบา |
| `/dashboard` | รายได้ · สถิติ · คำแนะนำ | ออเดอร์ + metrics + follower activity + แถวเบาทั้งหมด |
| `/core-prompt` | Core Prompt + SEO Prompt | core prompts ทั้งหมด |

**หน้าทำงานไม่ต้องโหลด core prompt** — ตรวจแล้วว่า `corePrompts` ถูกใช้เฉพาะใน `CorePromptPanel` เท่านั้น ส่วน `generateWithAI` อ่าน core prompt ที่ active เองฝั่ง server อยู่แล้ว

แท็บ ①②③④ ที่มีอยู่ (`components/workspace-tabs.tsx`) กลายเป็นลิงก์นำทางระหว่าง route จริง ผลพลอยได้: ปุ่ม back ของเบราว์เซอร์ทำงาน · แชร์/bookmark ลิงก์ตรงไปที่ entry ได้ · `/dashboard` เลิกโหลดตอนที่ผู้ใช้ไม่ได้เปิดดู

### 4.1 นิยาม "แถวเบา"

ฟิลด์ที่หน้ารายการและแถบข้างต้องใช้เท่านั้น:

```
id, productName, angle, videoUrl, postedAt, createdAt, duplicatedFromId,
productImages[0] (แค่ entryId + filename), มี chatgptOutput ไหม (boolean)
```

**ห้ามมี `chatgptOutput` · `productInfo` · `productSpec` · `riskModule` · `caption` · `hashtags`** — ประมาณ 1.6 KB/แถว แทนที่จะเป็น 12.4 KB (ลด 8 เท่า)

`มี chatgptOutput ไหม` ต้องเป็น boolean ที่คำนวณฝั่ง server ไม่ใช่ส่งข้อความมาแล้วเช็กฝั่ง client — เพราะตรรกะที่ใช้ (`isIncomplete` และ `collectUsedAngles`) ต้องการแค่ "ว่างหรือไม่ว่าง"

## 5. หน้ารายการ (`/`)

### 5.1 หน้าตา

คอลัมน์: **รูป · ชื่อสินค้าเต็ม · สถานะ · angle · วันที่ลงคลิป**

สถานะมี 3 ค่า ตรงกับที่ `isIncomplete` แยกอยู่แล้ว:
- ยังไม่มี prompt (ทั้ง `chatgptOutput` และ `videoUrl` ว่าง)
- รอลงคลิป (มี prompt แล้ว แต่ `videoUrl` ว่าง)
- ลงแล้ว

ตัวกรอง: ช่องค้นหา + สถานะ (ทั้งหมด / ยังไม่มี prompt / รอลงคลิป / ลงแล้ว)

**สถานะทั้งหมดอยู่ใน URL** (`/?q=แมว&status=pending&page=2`) ไม่ใช่ React state — กด back ได้ แชร์ลิงก์ผลค้นหาได้ รีเฟรชแล้วไม่หาย อ่านด้วย `searchParams` ซึ่งใน Next เวอร์ชันนี้เป็น `Promise` ต้อง `await`

การเรียงลำดับใช้ `sortEntriesForRail` เดิม (ยังไม่ลงคลิปอยู่บนสุด แล้วใหม่→เก่า) **ห้ามแก้ `lib/entry-sort.ts`**

### 5.2 ไม่มีคอลัมน์รายได้

เงินมี settlement lag 7+ วัน คลิปที่เพิ่งลงจะขึ้น ฿0 ทุกตัวแล้วอ่านเหมือนเจ๊งทั้งที่ยังไม่ถึงรอบจ่าย เหตุผลเดียวกับที่สเปกก่อนหน้า (`2026-07-28-sidebar-search-and-scan-design.md` หัวข้อ 6) ตัดสินใจไม่เอารายได้ใส่แถบข้าง รายได้อยู่ที่ `/dashboard` ซึ่งมีบริบทเรื่องรอบจ่ายครบ

### 5.3 pagination

30 แถว/หน้า ทั้งการกรอง การค้นหา และการนับรวมทำฝั่ง server ทั้งหมด

## 6. หน้าทำงาน (`/entry/[id]`, `/entry/new`)

### 6.1 แถบข้างผอมลง

เหลือ **15 รายการแรกตามลำดับของ `sortEntriesForRail` + ตัวที่กำลังเปิดอยู่**

"15 รายการแรก" หมายถึงลำดับเดิมของแถบข้างเป๊ะๆ คือ **ยังไม่ได้ลงคลิปขึ้นก่อน แล้วตามด้วยลงคลิปใหม่→เก่า** ไม่ใช่เรียงตาม `createdAt` ล้วน — เพราะของที่ยังไม่ลงคลิปคืองานที่ค้างอยู่ ต้องเห็นเสมอ

ถ้าตัวที่เปิดอยู่ไม่ติด 15 อันแรก ให้เพิ่มเข้าไปด้วยเสมอ ไม่งั้นผู้ใช้จะไม่เห็นว่าตัวเองอยู่ตรงไหน

**ตัดออกจาก `components/history-rail.tsx`:** ช่องค้นหา · ตัวกรอง "ยังไม่ได้กรอกผลลัพธ์" · หัวข้อกลุ่มตามเดือน · การจัดชั้นผลค้นหา · `showInfoMatches` · `railResetKey` (ไม่ต้องรีเซ็ต state ที่ไม่มีแล้ว)

**เพิ่ม:** ลิงก์ "ดูทั้งหมด" กลับไป `/` ที่ท้ายรายการ

ผลลัพธ์คือแถบข้างจะ**ง่ายลงและสั้นลง** ไม่ใช่ซับซ้อนขึ้น (จาก 305 บรรทัด)

การคลิกรายการในแถบข้างกลายเป็น `<Link href={/entry/${id}}>` แทน callback — ใช้ prefetch ของ Next ช่วยให้สลับเร็ว

### 6.2 เลข take

ปัจจุบันคำนวณจากตำแหน่งใน array เต็ม (`prompts.length - index`) พอไม่มี array เต็มแล้วต้องคำนวณฝั่ง server: จำนวน entry ทั้งหมด ลบ อันดับของ entry นี้ในลำดับเดียวกับ `sortEntriesForRail`

**เลขต้องคงที่เท่าเดิมสำหรับ entry เดิม** — ผู้ใช้เห็นเลขนี้เป็น T01/T02 บนหัวหน้าจอ ถ้าเลขเปลี่ยนไปจากเดิมคือ regression

### 6.3 Brief กับ ผลลัพธ์ ยังเป็นแท็บ

อยู่ใน `/entry/[id]` เป็น client state เหมือนเดิม เพราะใช้ข้อมูล entry ก้อนเดียวกัน

## 7. การค้นหาย้ายไปฝั่ง server

`lib/entry-search.ts` (`splitTerms` / `matchTier`) เป็น pure function ไม่มี dependency ใดๆ **ใช้ฝั่ง server ได้ทันทีโดยไม่ต้องแก้แม้แต่บรรทัดเดียว** — นี่คือผลตอบแทนของการแยกมันออกมาเป็นไฟล์ต่างหากตั้งแต่สเปกก่อนหน้า

วิธีทำ: หน้ารายการอ่าน `productName` + `extraNotes` + `productInfo` ของทุกแถว (เฉพาะ 3 คอลัมน์นี้) มาจัดชั้นด้วย `matchTier` ฝั่ง server แล้วส่งลง client เฉพาะ 30 แถวของหน้านั้น

**ต้นทุน:** ที่ 1,800 แถว = ~3.6 MB ในหน่วยความจำ server ต่อการค้น 1 ครั้ง ไม่ได้ส่งลง client เร็วพอสำหรับ SQLite บนเครื่องเดียว **ถ้าวันหนึ่งช้า ทางหนีคือ SQLite FTS5** ไม่ใช่การเปลี่ยนดีไซน์

การจัดชั้น 3 ระดับ (ตรงชื่อ / พบในโน้ต / พบในรายละเอียด) ยังใช้เหมือนเดิม แต่แสดงเป็นการเรียงลำดับในตารางแทนที่จะเป็นหัวข้อพับได้ — เพราะในหน้าที่มี pagination การพับหัวข้อทำให้จำนวนแถวต่อหน้าไม่แน่นอน

## 8. แผง angle กับสายเลือด

`collectFamily` (`lib/angle.ts`) ไต่ `duplicatedFromId` ขึ้นไปหา root แล้วแผ่ลงมา — ต้องรู้จัก entry ทุกตัว ไม่ใช่แค่ตัวที่เปิดอยู่

ส่งเฉพาะฟิลด์ที่ `collectUsedAngles` ใช้จริง: `id`, `duplicatedFromId`, `angle`, `videoUrl`, `postedAt` และ **`chatgptOutput` แทนด้วย boolean** (ตรรกะเช็กแค่ว่าว่างหรือไม่ เพื่อข้าม "ร่างเปล่า")

ที่ 1,800 แถว = ~180 KB ต่อการเปิดหน้าทำงาน 1 ครั้ง รับได้ **ห้ามแก้ `lib/angle.ts`** — เปลี่ยนแค่ shape ที่ส่งเข้าไป

`summarizeEntryOutcome` ต้องการ orders + metrics ด้วย โหลดเฉพาะที่เกี่ยวกับ entry ในสายเลือดนั้น ไม่ใช่ทั้งตาราง

## 9. `revalidatePath` — 20 จุดที่ต้องทบทวน

`app/actions.ts` เรียก `revalidatePath("/")` อยู่ 20 จุด ทุกจุดเขียนไว้ตอนที่แอปมีหน้าเดียว หลังแยก route แล้ว **`revalidatePath("/")` จะ revalidate เฉพาะหน้ารายการ ไม่แตะ `/entry/[id]` เลย**

เอกสารของ Next เวอร์ชันนี้ระบุ:
- `revalidatePath("/entry/abc123")` — path จริง revalidate หน้าเดียว ไม่ต้องใส่ `type`
- `revalidatePath("/entry/[id]", "page")` — route pattern revalidate ทุกหน้าที่ match **ต้องใส่ `type`**

หลักการ: action ที่แก้ entry ตัวเดียว ให้ revalidate path จริงของ entry นั้น + `/` (เพราะหน้ารายการโชว์ชื่อ/สถานะ) ส่วน action ที่แก้ core prompt ให้ revalidate `/core-prompt` และ action นำเข้าข้อมูลให้ revalidate `/dashboard`

**ต้องไล่ทีละจุดทั้ง 20 จุด** เอกสารระบุว่าปัจจุบัน Next ยัง refresh หน้าที่เคยเข้าไปแล้วให้ด้วยเมื่อกลับไปเยี่ยม แต่เป็นพฤติกรรมชั่วคราวที่จะเปลี่ยนในอนาคต **ห้ามพึ่งพฤติกรรมนี้**

## 10. สิ่งที่แลก (ยอมรับแล้ว)

**สลับ entry กลายเป็นการเปลี่ยนหน้า** — ปัจจุบันเป็น client state จึงทันที หลังแยก route มี round trip กระทบตอนเก็บงานเย็นที่ไล่วางลิงก์คลิปหลายตัวติดกัน บรรเทาด้วย prefetch ของ Next (`<Link>` prefetch ตอน hover) ผู้ใช้ยอมรับความเสี่ยงนี้แล้วโดยบอกว่า "ถ้าไม่เวิร์คก็ค่อย checkout กลับมา"

**ระหว่างทางแอปใช้งานไม่ได้เต็มที่** — ทำบน branch `feature/route-split-and-list-page` แล้ว merge ทีเดียวตอนเสร็จ **ห้าม merge ทีละส่วน** เพราะผู้ใช้ใช้แอปนี้ทำคลิปหาเงินทุกวัน

## 11. ความเสี่ยงและแผนถอย

นี่คือการรื้อโครงที่ใหญ่ที่สุดในโปรเจกต์นี้ — `components/prompt-workspace.tsx` (465 บรรทัด) ถือ state ทั้งหมดของแอปอยู่ตัวเดียว ต้องผ่าออกเป็นหลายหน้า ส่วนใหญ่เป็นการย้ายโค้ดมากกว่าเขียนตรรกะใหม่

ตาข่ายที่มี: `npx tsc --noEmit` · `npm run lint` · Playwright บน isolated dev server (พอร์ต 3001 + `dev-test.db`)

แผนถอย: branch แยก ยังไม่ merge จนกว่าจะเทียบกับของเดิมแล้วพอใจ ถ้าไม่เวิร์ค `git checkout master` แล้วทิ้ง branch

## 12. เกณฑ์ว่าสำเร็จ

1. เปิด `/` แล้ว payload ไม่โตตามจำนวน entry ทั้งหมด (30 แถว/หน้าคงที่)
2. `/dashboard` ไม่ถูกโหลดตอนอยู่หน้าอื่น
3. ค้นหาหลายคำยังให้ผลเท่าเดิมทุกเคสที่สเปกก่อนหน้าวัดไว้ (ตรรกะเดียวกัน ย้ายที่รันเฉยๆ)
4. เลข take ของ entry เดิมไม่เปลี่ยน
5. การเรียงลำดับในแถบข้างและหน้ารายการยังเหมือนเดิม (ยังไม่ลงคลิปบนสุด แล้วใหม่→เก่า)
6. ทุก mutation ยังเห็นผลทันทีในหน้าที่เกี่ยวข้อง (revalidatePath ครบ 20 จุด)
7. กดการ์ดคำแนะนำใน `/dashboard` แล้วไปที่ `/entry/<id>` ถูกตัว (แทนพฤติกรรม `openEntry` เดิม)

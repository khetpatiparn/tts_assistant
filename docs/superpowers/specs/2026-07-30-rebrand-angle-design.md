# Rebrand: "Angle by LAGR" — Design System

**วันที่:** 2026-07-30
**สถานะ:** อนุมัติแล้ว รอเขียน implementation plan

## 1. บริบท

ผู้ใช้ให้ feedback 3 ข้อหลังใช้แอปจริงหลัง route-split:
1. ฟอนต์ดูไม่สวย
2. ปุ่มต่างๆ มีแค่เส้นขอบ (stroke) ไม่บอกลำดับความสำคัญ ไม่ตรงหลัก UX ที่ดี
3. อยากให้ช่วยออกแบบ component อื่นให้เข้ากันด้วย

ระหว่างคุยพบว่านี่คือ**โปรเจกต์ที่ CLAUDE.md กันไว้แยกต่างหากแล้ว**: "ผู้ใช้กำลังจะเลิกธีมหนัง — การเปลี่ยนชื่อ+re-theme ทั้งแอปเป็นโปรเจกต์แยก" งานนี้จึงไม่ใช่แค่ปรับฟอนต์/ปุ่ม แต่คือการรีแบรนด์แอปทั้งตัว: ชื่อ, สี, ฟอนต์, ระบบ component, และคำศัพท์ที่ผูกกับธีมคลปเปอร์บอร์ด/หนัง (`ClapperHeader`, `takeNumber`, "Take 01", ไอคอน `Clapperboard`, `.clapper-stripes`)

กระบวนการที่ใช้ตัดสินใจ: เทียบ 3 ทิศทางกว้างๆ ก่อน (SaaS มินิมอล / อบอุ่นเป็นมิตร / มืออาชีพ) → ตัดสินใจว่าอยากได้ทิศทางแบบผสม ไม่ใช่ทิศทางสำเร็จรูป → เทียบ DESIGN.md จริงของ 4 ค่าย (Linear, Sentry, Mintlify, Claude — สกัดจาก [awesome-design-md](https://github.com/voltagent/awesome-design-md) ด้วย hex/font ค่าจริง ไม่ใช่ประมาณ) คู่กับ palette ที่ออกแบบใหม่ 1 ชุด → **เลือก palette ที่ออกแบบใหม่ ("Dusk Market")** → ปรับแก้ 2 รอบจาก feedback จริง (contrast ไม่ผ่าน WCAG, สีขาวจ้าเกินไป, เลย์เอาต์แถวเบียดกัน)

## 2. แบรนด์

- **ชื่อแอปใหม่:** **Angle** — เล่นเสียงพ้องกับ "Angel" โดยตั้งใจ (เชื่อมกับฟีเจอร์ angle tracking ที่เป็นหัวใจของแอป และคำแสลง "สินค้านางฟ้า" ในวงการขายของ TikTok)
- **Byline:** "by LAGR" — แสดงต่อท้ายชื่อแอปบนหัวเว็บทุกหน้า (เช่น "Angle · by LAGR")

## 3. สีพลิตต์ "Dusk Market" (ผ่าน WCAG AA แล้ว — วัดจริง ไม่ใช่ประมาณ)

### 3.1 กฎการใช้สี — แยก "สีแบรนด์ (action)" ออกจาก "สีสถานะ (semantic)"

นี่คือกฎที่สำคัญที่สุดของทั้งระบบ พลาดจุดนี้แล้วทุกอย่างจะดูสับสนเหมือนเดิม:

- **สีแบรนด์ (เทียล/อำพัน)** ใช้กับสิ่งที่ผู้ใช้ "เลือกทำ" เท่านั้น — ปุ่มหลัก 1 ปุ่มต่อหน้า, ตัวกรอง/แท็บ active
- **สีสถานะ (semantic)** ใช้กับสิ่งที่ "ระบบบอก" — ต้องเป็นสีที่**แยกเฉดหรือแยกบทบาทชัดจากสีแบรนด์** (เช่น badge "ลงแล้ว" ใช้เทียล**อ่อน/tint** ไม่ใช่เทียลเข้มเดียวกับปุ่ม) เพื่อไม่ให้สมองต้องแยกเองว่าสีนี้คือ "กดได้" หรือ "แค่บอกสถานะ"
- **สัดส่วน 60-30-10**: พื้นหลัง/กลาง ~60% ของหน้าจอ · โครงสร้าง (border/card) ~30% · สีเน้น (เทียล/อำพัน) เหลือแค่ ~10% — มีปุ่มพื้นทึบสีแบรนด์แค่ **1 ปุ่มต่อหน้า** (การกระทำหลักที่อยากให้ทำที่สุด) ปุ่ม/ตัวกรองอื่นใช้สีกลาง (ดำ/เทาเข้ม) ไม่ใช่สีแบรนด์

## 4. ฟอนต์

| บทบาท | ฟอนต์ | แทนที่ |
|---|---|---|
| Latin/ตัวเลข (display+body) | **Plus Jakarta Sans** | `Chonburi` (ถอดออกทั้งหมด) |
| ภาษาไทย (body) | **Noto Sans Thai** | `IBM Plex Sans Thai` |
| Label/ตัวเลข/โค้ด | **JetBrains Mono** (คงเดิม) | ไม่เปลี่ยน — ใช้ต่อเนื่องกับของเดิม |

ทั้งสองฟอนต์ใหม่โหลดผ่าน `next/font/google` เหมือนเดิม (`Plus_Jakarta_Sans`, `Noto_Sans_Thai` มีใน `next/font/google` ทั้งคู่ — ต้องตรวจชื่อ export จริงก่อนใช้ตอนเขียนโค้ด)

**เหตุผลที่ไม่ใช้ Inter (ที่ทั้ง Linear/Mintlify/Claude(fallback) ใช้):** Plus Jakarta Sans มี x-height และสัดส่วนใกล้เคียง Noto Sans Thai มากกว่า ทำให้ Latin/ตัวเลขกับภาษาไทยดูเป็นชุดเดียวกันมากกว่าตอนจับคู่กับ Inter

## 5. ระบบปุ่ม

| Variant | พื้น | ตัวหนังสือ | ใช้เมื่อ |
|---|---|---|---|
| Primary | `--teal` ทึบ | ขาว (light) / `#0a1f1c` (dark) | action หลักของหน้า — **1 ปุ่มต่อหน้าเท่านั้น** |
| Secondary | `--amber-soft` ทึบ + border | `--amber-ink` | action รอง (ทำซ้ำ, ดูทั้งหมด) |
| Ghost | โปร่งใส, hover เป็น `--border` | `--muted` → `--ink` ตอน hover | action เบาที่สุด (ยกเลิก) |
| Danger | `--red-soft` ทึบ | `--red` | ลบ/ทำลาย |
| Disabled | `--border` ทึบ, opacity 0.6 | `--muted` | cursor not-allowed |

**กฎ:** ปุ่มเดียวกัน (เช่น "ลบ") ต้องหน้าตาเดียวกันทุกที่ที่ปรากฏในแอป — ตอนนี้หลายจุด (`entry-list.tsx`, `production-panel.tsx`, `history-rail.tsx`) เขียน `className` สีเองแยกกัน (`bg-marigold text-ink hover:bg-marigold/90` ฯลฯ) ต้องรวมเป็น shared `Button` variant เดียว ห้ามมี custom color override กระจายอยู่ตามไฟล์อีก

**ปุ่มสลับ 2 ตัวเลือก** (เช่น "โพสต์สด/ตั้งเวลา" ใน `production-panel.tsx`) เปลี่ยนจากปุ่มแยก 2 ปุ่มเป็น segmented control ตัวเดียว (พื้น `--card`, ตัวเลือก active เป็น `--teal` ทึบ)

## 7. เลย์เอาต์แถวรายการ (หน้ารายการ + แถบข้าง)

ผ่านการเทียบ 3 รอบจาก feedback จริง:
1. **รอบแรก** (การ์ดแยกชิ้น) — โอเคแต่ไม่เห็นภาพรวมทั้งหน้า
2. **รอบสอง** (ตาราง fixed-column vs สองบรรทัด stacked) — ตารางตัดชื่อยาว (เจอจริง 125 ตัวอักษร) ไม่โอเค, สองบรรทัดชื่อไม่ตัดแต่ปล่อยพื้นที่ขวาโล่ง
3. **รอบสุดท้าย (อนุมัติแล้ว)** — ผสมสองแบบ:

```
[รูป] ชื่อสินค้า (wrap ได้ 2 บรรทัด ไม่ตัด)     │ สถานะ    วันที่    ยอดขาย    วิว
      angle: ...                              │ badge   12 ก.ค.   ฿1,240   3,204
```

- ฝั่งซ้าย (รูป+ชื่อ+angle) กว้างยืดหยุ่น (`flex:1`) ไม่ตัดชื่อ
- ฝั่งขวา (สถานะ/วันที่/ยอดขาย/วิว) จัดเป็นกลุ่มสถิติ 4 ช่อง แต่ละช่องมี label เล็กกำกับ (`สถานะ`/`วันที่`/`ยอดขาย`/`วิว`) คั่นจากฝั่งซ้ายด้วยเส้นบาง (`border-left`)
- **ช่องที่ไม่มีข้อมูลต้องหายไปทั้งช่อง ไม่ใช่โชว์ "—"** (เช่น entry ที่ยังไม่ได้ลงคลิปมีแค่ "สถานะ" กับ "สร้างเมื่อ" สองช่อง ไม่ต้องมี "ยอดขาย"/"วิว" ว่างๆ)
- ยอดขายที่มี pending แสดง tag "รอรอบจ่าย" (สีแดงอ่อน) ต่อท้าย ไม่ใช่แค่ตัวเลข ฿0 ลอยๆ

## 8. Empty state และข้อความระบบ

ยึดหลัก "ว่างเปล่า = คำเชิญให้ลงมือทำ" ไม่ใช่แค่บอกสถานะเฉยๆ:

- หน้ารายการว่างเพราะยังไม่มีข้อมูลเลย: ข้อความ + ปุ่มเพิ่มสินค้าแรกต่อท้าย
- หน้ารายการว่างเพราะกรองแล้วไม่เจอ: ข้อความ + ปุ่ม "ล้างตัวกรองทั้งหมด"
- **`confirm("ลบรายการนี้?")` (browser confirm ดิบ) ต้องเปลี่ยนคำให้บอกผลลัพธ์ที่กู้คืนไม่ได้ชัดเจน** เช่น "ลบรายการนี้ถาวร — กู้คืนไม่ได้" (เนื้อหา ยังใช้ `confirm()` เดิมได้ แค่เปลี่ยนคำ — เปลี่ยนเป็น custom dialog เป็นงานแยกถ้าอยากทำ ไม่บังคับในงานนี้)
- **คำกริยาต้องคงที่ตลอด flow เดียวกัน** — ปุ่ม "บันทึกผลลัพธ์" ต้องตามด้วยข้อความ "บันทึกแล้ว" เท่านั้น (ไม่ใช่ "สำเร็จ"/"เรียบร้อย" สลับกันไปมาคนละจุด)

## 10. ไม่ทำในงานนี้ (Non-goals)

- **ไม่สร้างกลไกสลับ dark mode จริง** (toggle switch) — งานนี้แค่เตรียม CSS variable ของทั้งสองโหมดให้พร้อม (`.dark` class มีอยู่แล้วแต่ไม่มีอะไรสลับ) ส่วนปุ่ม/กลไกสลับโหมดเป็นฟีเจอร์แยกถ้าต้องการภายหลัง
- **ไม่เปลี่ยน custom dialog แทน `confirm()`** — เปลี่ยนแค่ข้อความ ยังใช้ browser `confirm()` เดิม
- **ไม่แตะ `prisma/schema.prisma`** — งานนี้เป็น UI/CSS/copy ล้วน ไม่มี field ในฐานข้อมูลเกี่ยวข้อง
- **ไม่เปลี่ยนโครงสร้าง route/data-fetching** ที่เพิ่งทำเสร็จในสองแบรนช์ก่อนหน้า (route-split, list-page-ux-polish) — งานนี้แก้แค่ผิวหน้า (สี/ฟอนต์/component/คำศัพท์) ไม่แตะตรรกะ query/filter/pagination

## 11. ขนาดงานและความเสี่ยง

นี่คืองานที่แตะไฟล์เยอะที่สุดเท่าที่เคยทำในโปรเจกต์นี้ในเชิงจำนวนไฟล์ (แม้แต่ละไฟล์เปลี่ยนไม่มาก) เพราะสีเก่า (`ink`/`paper`/`marigold`/`rust`/`smoke`/`record`) ถูกใช้กระจายอยู่แทบทุก component ในแอป **implementation plan ต้องแบ่งเป็นหลาย task ตามกลุ่มไฟล์** (เช่น: tokens+fonts ก่อน → shared Button/Badge component → หน้ารายการ → หน้า entry → dashboard/core-prompt → cleanup คำศัพท์เดิม) ไม่ใช่แก้ทีเดียวทั้งแอปในคอมมิตเดียว เพื่อให้ตรวจทานได้ทีละก้อนและ rollback ง่ายถ้าพลาด

## 12. เกณฑ์ว่าสำเร็จ

1. ไม่มีคำว่า "Pooling Prompt", "Chonburi", "Clapperboard", "takeNumber", "sceneName", "clapper-stripes" เหลืออยู่ในโค้ดเลย (`grep` ยืนยันได้)
2. สีทุกคู่ (ตัวหนังสือบนพื้นหลัง) ผ่าน WCAG AA จริง (คำนวณ contrast ratio ไม่ใช่ดูตาเปล่า) ทั้ง light และ dark mode
3. ปุ่มที่ทำหน้าที่เดียวกัน (ลบ/ทำซ้ำ/ยกเลิก) หน้าตาเหมือนกันทุกจุดที่ปรากฏในแอป — ไม่มี custom color className กระจายอยู่ตามไฟล์

# หน้า "หาสินค้า" — สกัดสินค้าขายดีจากแคป TikTok Shop มาจัดอันดับ

## Context

ผู้ใช้เลือกสินค้าทำคลิปด้วยการเปิดหน้าจัดอันดับสินค้าใน TikTok Shop แล้วอ่านตัวเลขเอง — วันที่ 2026-08-16 แคปมา 14 รูปแล้วตัน ไม่รู้จะเริ่มตรงไหน เพราะต้องคำนวณ %ค่าคอมและเทียบดีมานด์ทีละรายการด้วยมือ (ผมคำนวณให้ในแชทใช้เวลาหลายนาทีต่อชุด) และ TikTok อัปเดตอันดับรายวัน

ฟีเจอร์นี้ยุบขั้นตอนนั้นเหลือ: แปะแคป → กดปุ่มเดียว → ได้ตารางจัดอันดับพร้อมคำตัดสิน → กดสร้าง entry ต่อได้ทันที

**ทำไมเรื่องนี้สำคัญ:** [[project-hero-clip-analysis]] สรุปว่าคุณภาพคลิปไม่ตัดสินยอดวิว ตัวแปรที่คุมได้จริงคือ **จำนวนคลิปที่ลง** กับ **สินค้าที่เลือก** — ฟีเจอร์นี้แก้ตัวแปรที่สอง และลดเวลาต่อรอบการเลือกสินค้า

### ข้อเท็จจริงที่ยืนยันจากรูปจริงแล้ว

โครงหน้าจอ TikTok Shop มี 3 ชั้น:

```
ชั้น 1  "สำหรับคุณ" หรือ "หมวดสินค้า"
          ↓
ชั้น 2  การ์ดหลายใบ (1 ใบ = 1 ประเภทย่อย โชว์ท็อป 3)
        มีแถบ "ขายดีที่สุด" กับ "คะแนนสูงสุด"
          ↓ กดเข้าการ์ด
ชั้น 3  รายการเต็ม 15 อันดับ  ← ฟีเจอร์นี้รับเฉพาะหน้านี้
```

| หน้า | ชื่อสินค้า | ราคา | ค่าคอม | ยอดขาย/สัปดาห์ |
|---|---|---|---|---|
| ชั้น 2 (การ์ด) | ❌ | ❌ | ✅ | ✅ |
| ชั้น 3 · ขายดีที่สุด | ✅ | ✅ | ✅ | ✅ |
| ชั้น 3 · คะแนนสูงสุด | ✅ | ✅ | ✅ | ❌ (โชว์ "รีวิวเชิงบวก 100.0%" แทน) |

**จึงรับเฉพาะ "ชั้น 3 · ขายดีที่สุด"** — ชั้น 2 ขาดราคา (คำนวณ %ค่าคอมไม่ได้) และขาดชื่อ (ระบุตัวสินค้าไม่ได้) ส่วนแถบคะแนนสูงสุดขาดยอดขาย ซึ่งเป็นครึ่งหนึ่งของสูตรดีมานด์รวม

**ทำไมไม่ทำ "เรดาร์หมวด" จากชั้น 2:** ไล่ดูทุกหมวดในแคป 14 รูปแล้ว **ไม่มีหมวดใหม่ที่ใช้ได้จริงแม้แต่หมวดเดียว** (ทุกหมวดที่ตรงทางคือหมวดที่ทำอยู่แล้ว ส่วนหมวดใหม่จริงคือ "อาหารสัตว์" ซึ่งผิดกฎเรื่องฉลากข้อความเยอะอยู่แล้ว) — คุณค่าที่คาดว่าจะได้ไม่มีอยู่จริงในข้อมูล และการเพิ่มชนิดแคปจะสวนทางกับปัญหาเดิมที่ว่า "แคปเยอะจนตัน"

## สูตรคำนวณ

```
%ค่าคอม    = ค่าคอม ÷ ราคา × 100
ดีมานด์รวม = ค่าคอม × ยอดขายต่อสัปดาห์
```

**%ค่าคอม** ตอบว่า "ถ้าขายได้ เราได้ส่วนแบ่งคุ้มไหม" · **ดีมานด์รวม** ตอบว่า "ตลาดอยากได้ของแบบนี้มากแค่ไหน" — ต้องดูคู่กัน เพราะสินค้าถูกที่ขายเยอะมากอาจดีกว่าสินค้าแพงที่แทบไม่มีคนซื้อ

## เกณฑ์ตัดสิน — เทียบกับผลงานจริงของตัวเอง ไม่ใช่เลขตายตัว

```
🟢 = %ค่าคอม สูงกว่า ค่าคอมจริงเฉลี่ยรวมทั้งร้าน
🔴 = ต่ำกว่า
```

**ค่าเทียบคือ `settled รวม ÷ GMV รวม` จาก `AffiliateOrder` ทั้งหมดที่ settle แล้ว** (ณ 2026-08-16 = 6.5%) คำนวณสดทุกครั้งที่เปิดหน้า

**ทำไมเลือกแบบนี้ (สำคัญ — อย่าเปลี่ยนเป็นเลขตายตัว):**
- ระบบนี้เคยพังจากเกณฑ์ตั้งเองมาแล้ว 2 ครั้ง — `CLIP_AWAITING_THRESHOLD` ติด active ถาวรโดยไม่มีใครสังเกต และ growing-threshold ที่เทียบกับ median ของกลุ่มตัวเอง (ดู [[project-weekly-task-panel]])
- เกณฑ์นี้ **ปรับตัวเองตามข้อมูลจริง** ไม่ต้องกลับมาแก้เมื่อธุรกิจโต
- **ใช้ค่าเดียวรวมทุกหมวด ไม่แยกรายหมวด** เพื่อเลี่ยงตารางจับคู่หมวดในโค้ดที่ต้องคอยดูแล และเพื่อให้หมวดที่ไม่เคยขายมาก่อนก็ยังมีค่าเทียบเสมอ (ถ้าภายหลังพบว่าอยากแยกรายหมวดจริง ค่อยเพิ่มได้ — เป็นการเพิ่ม ไม่ใช่รื้อ)

**ดีมานด์รวมใช้เรียงลำดับอย่างเดียว ไม่มีคำตัดสินผ่าน/ไม่ผ่าน** — เพราะไม่มีค่าอ้างอิงจากข้อมูลตัวเองมาเทียบ (ผู้ใช้ไม่มียอดขายระดับแพลตฟอร์มของสินค้าตัวเอง) การตั้งเส้นแบ่งเองจะเป็นเลขลอยๆ ซึ่งเป็นสิ่งที่หลีกเลี่ยง

## ธงเตือน — ตรวจจากชื่อสินค้าด้วยโค้ด ไม่ใช้ AI

ชื่อสินค้าไทยบอกกลไกตรงๆ อยู่แล้ว ตรวจด้วยการหาคำในชื่อได้เลย ไม่ต้องให้ AI ตัดสิน (ถูกกว่า เร็วกว่า ทดสอบได้)

| ธง | คำที่ตรวจ | เหตุผล |
|---|---|---|
| ⚠️ อาจมีกลไก | พับได้ · พับ · หมุน · 360 · ยืด · ปรับระดับ · อัตโนมัติ · สไลด์ · บานพับ | [[project-caption-driven-mechanism-selection]] — สินค้ามีกลไกซ้อนทำให้ AI เลือกกลไกผิด |
| ⚠️ อาจมีข้อความเยอะ | อาหาร · ขนม · ผง · น้ำยา · ครีม · เจล · วิตามิน · อาหารเสริม | ฉลาก/ตารางโภชนาการทำให้ AI generate เพี้ยน (บันทึกไว้ใน [[project-product-sourcing-automation-parked]]) |

**ธงเป็นแค่คำเตือน ไม่ใช่การกรองทิ้ง** — แถวยังขึ้นตามปกติ ผู้ใช้ตัดสินเอง

## หน้าตาและการใช้งาน

หน้าใหม่ที่ route `/products` เพิ่มเข้าเมนูหลักใน `components/app-header.tsx` ชื่อ **"หาสินค้า"** (NavKey ใหม่: `products`)

### แถบเตือนกันลืม (บนสุด แสดงตลอด)

```
💡 หมวดที่ควรโฟกัส — อ้างอิงค่าคอมจริงจากยอดขายของคุณเอง
   เครื่องครัว 8.5% (17 ออเดอร์) · สัตว์เลี้ยง 7.5% (285) · จัดระเบียบบ้าน 5.9% (260)
   แคปจากหน้า "ขายดีที่สุด" (ชั้น 3 · 15 อันดับ) เท่านั้น
```

**ต้องแสดงจำนวนออเดอร์กำกับทุกหมวดเสมอ** — ณ 2026-08-16 เครื่องครัวมี %สูงสุดแต่มาจากแค่ 17 ออเดอร์ ขณะที่สัตว์เลี้ยงมี 285 ออเดอร์ ถ้าโชว์แต่ % จะอ่านผิดว่าเครื่องครัวดีกว่าทั้งที่ตัวเลขยังไม่นิ่ง

ตัวเลขคำนวณสดจาก `AffiliateOrder` โดยจับกลุ่มหมวดจากคำในชื่อสินค้า (แมว/หมา/สัตว์ → สัตว์เลี้ยง · หม้อ/กระทะ/ช้อน/ครัว → ครัว · ชั้นวาง/รถเข็น/กล่องเก็บของ → จัดระเบียบบ้าน)

**เป็นป้ายเตือนล้วน ไม่กรองอะไรทั้งสิ้น** — แคปหมวดอื่นมาก็ใช้ได้ปกติ ระบบไม่มีรายชื่อหมวดที่อนุญาต/ห้ามในโค้ด

**หมายเหตุความไม่สมมาตรที่ตั้งใจ:** แถบนี้ใช้การจับกลุ่มหมวดด้วยคำ (keyword mapping) ทั้งที่หัวข้อ "เกณฑ์ตัดสิน" ด้านบนจงใจเลี่ยงการจับกลุ่มหมวด — **ไม่ขัดกัน** เพราะแถบนี้เป็นข้อความเตือนเฉยๆ ถ้าจับกลุ่มพลาดก็แค่เลขบนป้ายคลาดเคลื่อน ไม่มีอะไรพัง ส่วนเกณฑ์ 🟢/🔴 ขับการตัดสินใจจริงจึงต้องใช้ค่าที่ไม่มีทางเพี้ยน (settled ÷ GMV รวม) **ห้ามเอา keyword mapping นี้ไปใช้กับเกณฑ์ตัดสิน**

### สรุปหมวดที่เก็บมาแล้ว (ใต้แถบเตือน)

```
📦 เก็บมาแล้วในระบบ
   ที่เก็บของและชั้นวาง  15 รายการ · เก็บล่าสุด 16 ส.ค.
   ของเล่นแมว           15 รายการ · เก็บล่าสุด 16 ส.ค.
   เครื่องครัว            12 รายการ · เก็บล่าสุด 9 ส.ค. ⚠️ 7 วัน
   [กดชื่อหมวดเพื่อกรอง]
```

เตือน ⚠️ เมื่อหมวดนั้นเก็บล่าสุดเกิน 7 วัน (ใช้ `IMPORT_STALE_DAYS` จาก `lib/import-schedule.ts` ที่มีอยู่แล้ว ไม่ตั้งค่าคงที่ใหม่)

### กล่องแปะรูป

แปะได้หลายใบพร้อมกัน (paste/เลือกไฟล์) แบบเดียวกับแผงสกัดใน `brief-form.tsx` — **รูปอยู่ใน memory เท่านั้น ไม่เขียนดิสก์ ไม่สร้างแถว `ProductImage`** เพราะเป็นแคปหน้าจัดอันดับ ไม่ใช่รูปสินค้าจริง ปนกันแล้ว 10-part prompt จะเพี้ยน

ปุ่ม **"อ่านข้อมูลจากรูป"** → เล่นเสียงแจ้งเตือนตอนจบผ่าน `playCompletionSound` ที่มีอยู่แล้ว

### ตารางผลลัพธ์

เรียงตามดีมานด์รวมจากมากไปน้อย แต่ละแถวแสดง:

```
🟢 HEINO กว้าง 40CM 5 ชั้น ตู้เก็บของพับได้
   ราคา 249 · ค่าคอม 29.90 · ขายได้ 13,900/สัปดาห์
   ▸ ได้ 12.0% — ดีกว่าค่าคอมจริงเฉลี่ยของคุณ (6.5%)
   ▸ ดีมานด์รวม 415,610
   ⚠️ ชื่อมีคำว่า "พับได้" — อาจมีกลไก ตรวจรูปก่อนทำ
   [ สนใจ ] [ ปัดตก ] [ สร้างงานเลย ]
```

แถวที่ขาดยอดขาย (แคปผิดหน้ามาจาก "คะแนนสูงสุด") แสดงเตือนแทนการคำนวณมั่ว:

```
⚠️ แถวนี้ไม่มีตัวเลขยอดขาย (น่าจะมาจากหน้า "คะแนนสูงสุด")
   จัดอันดับให้ไม่ได้ — ลองแคปจากหน้า "ขายดีที่สุด" แทน
```

### ปุ่ม 3 ปุ่ม

| ปุ่ม | ทำอะไร |
|---|---|
| สนใจ | `status = "interested"` เก็บไว้ในลิสต์ ยังไม่ทำ |
| ปัดตก | `status = "rejected"` ซ่อนจากตารางหลัก และไม่โผล่อีกแม้แคปเจอซ้ำ |
| สร้างงานเลย | สร้าง `PromptEntry` ใหม่ (ชื่อสินค้าเติมให้) + `status = "done"` + ผูก `linkedEntryId` |

มีตัวกรองสถานะด้านบนตาราง (ทั้งหมด / ยังไม่ตัดสิน / สนใจ / ปัดตก) — ค่าเริ่มต้นซ่อน `rejected`

## โครงข้อมูล

### ตารางใหม่ `ProductCandidate`

```prisma
model ProductCandidate {
  id            String   @id @default(cuid())
  /// ชื่อเต็มตามภาพ ไม่ย่อ — ใช้เป็นตัวระบุตัวตนตอนกันซ้ำ
  name          String
  /// normalize แล้ว (ตัดช่องว่างซ้ำ, lowercase) ใช้จับคู่ตอน upsert
  nameKey       String   @unique
  price         Float
  commission    Float
  /// null = แคปมาจากหน้าที่ไม่มีตัวเลขยอดขาย (คะแนนสูงสุด)
  weeklySales   Int?
  /// ชื่อหมวดที่ AI อ่านจากหัวข้อบนสุดของภาพ
  categoryLabel String
  capturedOn    DateTime
  /// "new" | "interested" | "rejected" | "done"
  status        String   @default("new")
  note          String   @default("")
  linkedEntryId String?
  createdAt     DateTime @default(now())

  @@index([status])
  @@index([categoryLabel])
}
```

**สิ่งที่จงใจไม่เก็บ:**
- **`%ค่าคอม` และ `ดีมานด์รวม`** — คำนวณสดจาก 3 ช่องที่เก็บไว้ ตรงกับที่ `lib/dashboard.ts` ทำ (aggregation ล้วน ไม่เก็บผลลัพธ์)
- **ประวัติราคา/ยอดขายย้อนหลัง** — ไม่ทำ snapshot แบบ `ClipMetric` เพราะการเลือกสินค้าสนใจดีมานด์ปัจจุบัน และ [[project-analysis-limits]] บอกว่าข้อมูลระดับนี้แยก "เทรนด์จริง" กับ "ดวง" ไม่ได้อยู่แล้ว
- **ไม่ผูก relation กับ `PromptEntry`** — เก็บ `linkedEntryId` เป็น String เปล่าๆ ไม่ทำ foreign key เพราะ candidate ควรอยู่รอดได้แม้ entry ถูกลบ (ประวัติการตัดสินใจไม่ควรหายตาม)

### การกันข้อมูลซ้ำ

TikTok อัปเดตอันดับรายวัน สินค้าเดิมจะโผล่ซ้ำแน่นอน — ใช้ `upsert` ด้วย `nameKey`:

```
เจอชื่อเดิม  → อัปเดต price / commission / weeklySales / categoryLabel / capturedOn
             → คง status / note / linkedEntryId เดิมไว้ (ปัดตกแล้วไม่กลับมา)
ไม่เจอ       → สร้างแถวใหม่ status = "new"
```

ถ้าจับคู่พลาด (AI อ่านชื่อเพี้ยนเล็กน้อย) จะได้แถวซ้ำที่**มองเห็นและกดปัดตกได้** — ล้มเหลวแบบไม่เสียหาย ดีกว่าใช้ fuzzy matching ที่อาจรวมสินค้าคนละตัวเข้าด้วยกันเงียบๆ

## การสกัดข้อมูลจากภาพ

### `lib/gemini.ts` — เพิ่ม `extractProductCandidates`

ล็อกโมเดลไว้ที่ `EXTRACT_MODEL` (flash-lite) เหมือน `extractProductFields` เดิม — เป็นงานอ่านข้อความจากภาพ ไม่ใช่งานตีความภาพเชิงลึก · `temperature: 0`

**ฟอร์แมตผลลัพธ์ — บรรทัดละ 1 สินค้า คั่นด้วย `|`:**

```
หมวด: <ชื่อหมวดจากหัวข้อบนสุดของภาพ>
<ชื่อสินค้าเต็ม> | <ราคา> | <ค่าคอม> | <ยอดขาย>
<ชื่อสินค้าเต็ม> | <ราคา> | <ค่าคอม> | <ยอดขาย>
```

เลือกฟอร์แมตนี้เพราะแยกวิเคราะห์ทีละบรรทัดได้ — บรรทัดที่ผิดรูปข้ามเฉพาะบรรทัดนั้น ไม่ทำให้ทั้งชุดเสีย (ปรัชญาเดียวกับ `lib/caption.ts`)

**กติกาในพรอมต์:** ชื่อสินค้าเอาเต็มตามภาพ ห้ามย่อ (ต่างจาก `EXTRACT_INSTRUCTION` เดิมที่ให้ย่อ 2-5 คำ) เพราะชื่อเต็มคือตัวระบุตัวตนตอนกันซ้ำ · ถ้าช่องไหนไม่มีในภาพให้ใส่ `-`

### `lib/candidates.ts` (ไฟล์ใหม่) — parser + คำนวณ ล้วนๆ ไม่มี I/O

ทดสอบแยกได้ ไม่ต้องพึ่ง DB หรือ Gemini:

```ts
parseCandidateLines(raw: string): ParsedCandidate[]
parseThaiNumber(text: string): number | null   // "13.9K" → 13900, "฿29.90" → 29.90
                                                // "฿17.52 – 21.90" → 17.52 (ใช้ค่าต่ำสุด conservative)
normalizeName(name: string): string             // ตัดช่องว่างซ้ำ + lowercase
detectFlags(name: string): CandidateFlag[]      // ธงกลไก/ข้อความ
commissionPercent(c: ProductCandidate): number
demandTotal(c: ProductCandidate): number | null // null ถ้าไม่มี weeklySales
```

**จุดที่ต้องระวังเป็นพิเศษ (มีเคสจริงในภาพแล้ว):**
- `13.9K` / `1.4K` / `816` — suffix K ต้องคูณ 1,000
- `฿17.52 – 21.90` — ราคาช่วง ใช้ค่าต่ำสุด (สอดคล้องกับหลัก "เลือกทางที่ conservative" ใน Core Prompt)
- `รับ ฿0.96` — ทศนิยม 2 ตำแหน่ง ต้องไม่ปัดทิ้ง

### `app/actions.ts` — 3 action ใหม่

```ts
extractCandidates(formData)              // รูป → Gemini → parse → upsert → revalidate
setCandidateStatus(id, status, note?)    // สนใจ / ปัดตก
createEntryFromCandidate(id)             // สร้าง PromptEntry + ผูก linkedEntryId + status = done
```

`createEntryFromCandidate` ทำตามแบบ `createEntryFromOrder` ที่มีอยู่แล้ว (สร้าง entry ขั้นต่ำ ผูก `corePromptId` ที่ active อยู่ **โดยต้องใส่ `kind: "core"` ใน where เสมอ** ไม่งั้นได้ SEO prompt มาแทน)

## Error handling

| กรณี | ทำอะไร |
|---|---|
| ไม่มี `GEMINI_API_KEY` | throw ข้อความไทยบอกให้ตั้งค่า (แบบเดียวกับ action อื่น) |
| AI ตอบว่าง | throw "AI ไม่ได้ตอบกลับ ลองใหม่อีกครั้ง" |
| บรรทัดผิดรูป | ข้ามเฉพาะบรรทัดนั้น ไม่ throw — แสดงจำนวนที่ข้ามให้ผู้ใช้เห็น |
| ไม่มี `weeklySales` | เก็บเป็น `null` แสดงเตือนในแถว ไม่คำนวณดีมานด์รวม |
| ไฟล์ไม่ใช่รูป / ใหญ่เกิน 10MB | ใช้ `ALLOWED_IMAGE_TYPES` / `MAX_IMAGE_BYTES` ที่มีอยู่แล้ว |
| ยังไม่มีออเดอร์ settle เลย (ค่าเทียบ = 0) | ไม่แสดง 🟢/🔴 แสดงแค่ %ค่าคอมเปล่าๆ พร้อมโน้ตว่ายังไม่มีข้อมูลเทียบ |

## Global Constraints

- ห้ามรัน `npm run build`/`npm run dev` ชน port 3000 — ใช้ `npx tsc --noEmit` + `npm run lint` + isolated dev server
- หลังแก้ `prisma/schema.prisma` ต้อง `npx prisma migrate dev --name add-product-candidate` แล้ว `npx prisma generate`
- ห้าม hex / arbitrary font size ใน `components/*` · ใช้ design token เดิม
- `line-height` ข้อความไทยขั้นต่ำ 1.6 · ห้าม `font-mono` กับข้อความไทย (มี glyph ไทยไหม ต้องเช็คตอน runtime ไม่ใช่ดูจาก source — เคยพลาดมาแล้วกับ `toLocaleDateString("th-TH")`)
- UI ภาษาไทย ห้าม emoji ในโค้ด (ใช้ไอคอน lucide แทน)
- `@prisma/client` import จาก `@/lib/generated/prisma/client` เท่านั้น
- แก้สีต้องรัน `node scripts/check-contrast.mjs` ให้ผ่าน

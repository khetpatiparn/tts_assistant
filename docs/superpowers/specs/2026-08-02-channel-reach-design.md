# นำเข้า Overview.csv — วิวทั้งช่องและ conversion ที่ไม่มี selection bias

**วันที่:** 2026-08-02

## ปัญหา

`Content.csv` จาก TikTok Studio ให้ข้อมูลได้สูงสุด **15 แถวต่อการ export 1 ครั้ง** และเป็น "ท็อป 15 ตามวิว" ของช่วงที่เลือก ผลคือตอนนี้ระบบมีข้อมูลวิวแค่ **33 คลิปจาก 78 คลิป (42%)** และคลิปที่หายไปคือคลิปวิวน้อยทั้งหมด

นี่ไม่ใช่แค่ "ข้อมูลไม่ครบ" แต่เป็น **selection bias เชิงระบบ** — เราเห็นแต่คลิปที่สำเร็จ ไม่เคยเห็นคลิปที่ล้ม ทำให้:

- ค่ากลางของวิวสูงเกินจริง (เคยวัดได้ 1,828 ตอนมีแต่ท็อป 15 พอเติมคลิปวิวน้อยเหลือ 1,538)
- อัตราการเจอ winner ดูดีเกินจริง
- **การวิเคราะห์เวลาโพสต์เชื่อไม่ได้** เพราะหาความสัมพันธ์ "ชั่วโมงที่โพสต์ vs วิว" จากกลุ่มตัวอย่างที่ถูกคัดมาด้วยวิวตั้งแต่แรก = วนกลับมาหาตัวเอง
- ข้อสรุป "conversion คงที่ 0.2–0.3%" คำนวณจากคลิป winner ล้วน พิสูจน์ไม่ได้ว่าจริงกับทั้งช่อง

`Overview.csv` (ไฟล์ที่ TikTok Studio ให้มาพร้อมกันแต่ยังไม่เคยนำเข้า) ให้ **วิวรวมทั้งช่องต่อวัน แบบไม่มีเพดาน** พอจับคู่กับวันที่ในไฟล์ออเดอร์ (ซึ่งครบ 100% อยู่แล้วเพราะ xlsx ไม่มี cap) จะได้ conversion ระดับช่องที่ไม่มี bias

**พิสูจน์แล้วกับข้อมูลจริง** (ไฟล์ตัวอย่าง 13 มิ.ย.–10 ก.ค. ใน `data_last28days/`):

| ช่วง | วิวทั้งช่อง | ออเดอร์ | conv |
|---|---|---|---|
| 13–30 มิ.ย. (ยังไม่มี winner) | 7,913 | 10 | 0.126% |
| 1–10 ก.ค. (มีที่ลับเล็บแมวแล้ว) | 16,685 | 46 | 0.276% |
| **รวม 28 วัน** | **24,598** | **56** | **0.228%** |

ค่ารวม 0.228% ตรงกับที่คำนวณจากคลิป winner (0.20–0.29%) → ยืนยันว่าสมมติฐาน "วิวคือ lever" ไม่ใช่ภาพลวง แต่ตัวเลขที่ขยับ 2.2 เท่าระหว่างสองช่วงบอกว่า **การเลือกสินค้าก็มีผลราว 2 เท่า** ไม่ใช่วิวอย่างเดียว

## เป้าหมาย

ตอบ 2 คำถามด้วยข้อมูลที่ไม่มี bias:

1. **การเลือกสินค้าดีขึ้นหรือแย่ลง** — conversion ทั้งช่องเทียบข้ามสัปดาห์
2. **ช่องกำลังโตขึ้นหรือเปล่า** — วิวรวมต่อสัปดาห์แบบครบทุกคลิป

## สิ่งที่ตัดออกโดยตั้งใจ

- **ไม่คำนวณ "วิวของคลิปที่ไม่ติด top-15"** — วิวใน `Content.csv` เป็นยอดสะสมของคลิป ส่วนวิวใน `Overview.csv` เป็นวิวที่ได้เพิ่มรายวัน ลบกันตรงๆ ไม่ได้ ต้องจับคู่ snapshot สองรอบแล้วหาส่วนต่างซึ่งได้แค่ค่าประมาณ และต่อให้รู้ก็ไม่เปลี่ยนพฤติกรรม (คำตอบคือ "export ให้ถี่ขึ้น" อยู่แล้วไม่ว่าตัวเลขจะเป็นเท่าไร)
- **ไม่ทำกราฟ** — ข้อมูลมี ~10 สัปดาห์ อ่านเป็นตารางได้สบาย และคอลัมน์ conv% ที่หารมาให้แล้วอ่านแม่นกว่าการกะสายตาว่าเส้นสองเส้นวิ่งตามกันไหม เพิ่มทีหลังได้โดยไม่ต้องรื้อ (ข้อมูลชุดเดียวกัน)
- **ไม่นำเข้าอีก 4 ไฟล์ใน `data_last28days/`** — ตรวจแล้วไม่มีอันไหนเปลี่ยนการตัดสินใจ: `Viewers.csv` (ผู้ชมใหม่ ~99% ทุกวัน รู้แล้วก็ไม่เปลี่ยนอะไรเพราะโมเดลไม่ได้พึ่งคนดูซ้ำ) · `FollowerHistory.csv` (28 วันได้ผู้ติดตามเพิ่ม 6 คน เส้นแบน) · `FollowerGender.csv` (53/47 ไม่มีสัญญาณ) · `FollowerTopTerritories.csv` (เป็นสัดส่วนของผู้ติดตาม ไม่ใช่ผู้ชม และ 99% ของคนดูไม่ใช่ผู้ติดตาม จึงบอกอะไรเกี่ยวกับคนซื้อไม่ได้)

## สถาปัตยกรรม

### 1. ตาราง `ChannelMetric`

```prisma
model ChannelMetric {
  id           String   @id @default(cuid())
  statsOn      DateTime @unique
  videoViews   Int
  profileViews Int
  likes        Int
  comments     Int
  shares       Int
  importedAt   DateTime @default(now())
}
```

ชื่อคู่กับ `ClipMetric` (รายคลิป) → `ChannelMetric` (รายช่อง) · `statsOn` ตามคอนเวนชัน `activityOn`/`capturedOn` ที่มีอยู่ · `@unique` ทำให้ upsert ได้ โยนไฟล์เดิมซ้ำไม่เกิดแถวซ้ำ (แบบเดียวกับ `FollowerActivity`)

**เก็บทุกคอลัมน์แม้จะแสดงแค่ `videoViews`** เพราะ `Overview.csv` ให้ย้อนหลังแค่ 28 วัน ถ้าไม่เก็บตอนนี้ ข้อมูลเก่าจะหายถาวรกู้ไม่ได้ — ต่างจากไฟล์รายได้ (xlsx) ที่ import ย้อนหลังได้เสมอ ต้นทุนคือคอลัมน์ integer เพิ่ม 4 ตัว

### 2. Parser `lib/channel-metrics.ts`

ใช้ `parseCsvRows` + `parseMonthDayLabel` จาก `lib/csv.ts` ที่มีอยู่ ไม่เขียน BOM-strip/quoted-field parser ซ้ำ

ตำแหน่งคอลัมน์ (0-based) ใน `Overview.csv`:

```
0 = Date ("June 13")   1 = Video Views   2 = Profile Views
3 = Likes              4 = Comments      5 = Shares
```

**กฎ 2 ข้อที่ห้ามพลาด:**

1. **ค่าติดลบต้องเก็บตามจริง** — คอลัมน์ Comments มีค่าติดลบได้ (พบจริง `"June 20" = -6` คอมเมนต์ถูกลบ) `parseInt` รองรับอยู่แล้ว แต่ต้องมีเทสต์ล็อกไว้กันคนมาเติม `Math.abs`/`Math.max(0, …)` ทีหลัง
2. **แถวที่ `Video Views` ไม่ใช่ตัวเลข (เช่น `"undefined"`) ต้องข้ามทั้งแถว ไม่ใช่บันทึกเป็น 0** — พบจริงใน `Viewers.csv` (วันที่ยังไม่มีข้อมูล) ถ้าบันทึก 0 จะทำให้ conversion เพี้ยนเพราะตัวหารหายไปทั้งที่จริงๆ ไม่รู้ค่า

### 3. Server Action `importChannelMetrics`

ลอกโครงจาก `importFollowerActivity` ใน `app/actions.ts`:

- ไม่มีไฟล์ / ไฟล์ว่าง → `throw` พร้อมข้อความบอกชื่อไฟล์ที่ต้องการ
- parse ล้มเหลว → `throw "อ่านไฟล์ไม่สำเร็จ — ต้องเป็นไฟล์ Overview (.csv) จาก TikTok Studio"`
- ไม่พบแถวที่ใช้ได้เลย → `throw`
- upsert ทีละแถวด้วย `statsOn`
- `revalidatePath("/dashboard")`
- คืน `{ total, skipped, firstDate, lastDate }`

`skipped` มีไว้บอกจำนวนแถวที่ถูกข้าม (ค่าไม่ใช่ตัวเลข/วันที่อ่านไม่ออก) เพื่อไม่ให้การข้ามเงียบ

### 4. Aggregation `lib/channel-reach.ts` (pure)

รับ `ChannelMetric[]` + ออเดอร์ → คืน:

- แถวรายสัปดาห์ `{ weekStart, views, orders, convPct }` **เรียงใหม่→เก่า** แสดงทุกสัปดาห์ที่มีข้อมูล (ไม่ตัด — โตแค่สัปดาห์ละแถว)
- สรุปหัวตาราง `{ views30d, conv30d, convPrev30d }` โดย **"30 วันล่าสุด" นับถอยจากวันที่มีข้อมูลล่าสุดใน `ChannelMetric` ไม่ใช่จากวันนี้** (ถ้านับจากวันนี้ ช่วงที่ยังไม่ได้ import จะถูกนับเป็นวิว 0 แล้วลาก conversion ให้เพี้ยน) ส่วน `convPrev30d` คือ 30 วันก่อนหน้านั้นอีกช่วง ใช้เป็นตัวเทียบของลูกศร ▲/▼

สัปดาห์เริ่มวันเดียวกับ Weekly Scoreboard เพราะใช้ helper ตัวเดียวกัน — ตัวเลขสองแผงจึงเทียบกันได้ตรงๆ

**จุดที่พังง่ายที่สุดของงานนี้ — การจัดสัปดาห์:**

- `statsOn` เก็บเป็น UTC midnight (มาจาก `parseMonthDayLabel` ที่ใช้ `Date.UTC`) → ต้องใช้ **`weekStartOfPostedAt`** (UTC getter)
- `orderDate` เป็น timestamp จริง → ต้องใช้ **`weekStartOfLocal`** (local getter)

ทั้งคู่ export อยู่แล้วใน `lib/weekly-scoreboard.ts` **สลับกันเมื่อไรสัปดาห์จะเหลื่อมทันที** เป็นบั๊กคลาสเดียวกับ `toDateInputValue`/`toLocalDateInputValue` ที่ CLAUDE.md เตือนไว้ ต้องมีคอมเมนต์กำกับตรงจุดที่เรียกใช้

**กันหารศูนย์:** สัปดาห์ที่มีออเดอร์แต่ไม่มีข้อมูลวิว (`views === 0`) ต้องคืน `convPct: null` แล้ว UI แสดง `—` ไม่ใช่ `Infinity` หรือ `NaN`

### 5. UI

**`components/channel-reach-panel.tsx`** (คอมโพเนนต์ใหม่ ตาม pattern ของ `revenue-by-clip.tsx` / `post-time-panel.tsx`):

วิวทั้งช่อง 30 วัน: 56,985     conversion: 0.28%  ▲ จาก 0.13%
                                (เทียบ 30 วันก่อนหน้า)

สัปดาห์      วิวทั้งช่อง   ออเดอร์   conv%

20 ก.ค.         9,024        51    0.57%
13 ก.ค.        21,096       126    0.60%

ลูกศรแสดงเมื่อมีข้อมูลครบทั้งสองช่วงเท่านั้น ถ้าช่วงก่อนหน้าไม่มีข้อมูล (เพิ่งเริ่ม import) ให้ซ่อนลูกศรไปเลย ไม่ใช่แสดง ▲ จาก 0%

**`components/dashboard-panel.tsx`** — เพิ่มฟอร์มอัปโหลดตัวที่ 4 ในกล่อง import (ลอก `useActionState` block ของ `importFollowerActivity`)

**ข้อความกำกับใต้ตาราง (บังคับต้องมี):**

> ออเดอร์นับตามวันที่สั่งซื้อ ส่วนวิวนับตามวันที่เกิดวิว — คนดูคลิปวันนี้อาจไปสั่งพรุ่งนี้ ดังนั้น conv% รายสัปดาห์เป็นค่าประมาณ ใช้ดูแนวโน้มข้ามหลายสัปดาห์ได้ แต่อย่าอ่านสัปดาห์เดียวแล้วสรุป

เหตุผลที่ต้องมี: ป้องกันการอ่านผิดแบบเดียวกับที่ `post-time-panel.tsx` ต้องเขียนว่า "ยังน้อยเกินจะสรุป" — ตัวเลขที่ดูแม่นยำแต่มี lag ซ่อนอยู่คือกับดักที่แย่กว่าตัวเลขที่บอกตรงๆ ว่าไม่แน่นอน

## การใช้งานจริง (สำคัญต่อคุณค่าของฟีเจอร์)

`Overview.csv` ให้ย้อนหลัง **28 วัน** ต่อการ export 1 ครั้ง ต่างจาก `Content.csv` ตรงที่**ไม่มีเพดานจำนวนแถว** — ข้อมูลครบทุกวันในช่วงนั้น ดังนั้น:

- **export ทุก ≤28 วันจะได้ประวัติต่อเนื่องแบบไม่ขาด** (ถ้าเว้นนานกว่านั้นจะมีช่วงที่หายถาวร)
- ไฟล์ตัวอย่างที่มีอยู่แล้วใน `data_last28days/` ครอบคลุม 13 มิ.ย.–10 ก.ค. ซึ่งเป็นช่วงที่ระบบ**ไม่มีข้อมูลวิวเลยสักวัน** (`ClipMetric` เริ่มที่ 21 ก.ค.) → อัปไฟล์เก่านี้เข้าไปได้ประวัติเพิ่มฟรี 1 เดือน

## การทดสอบ

โปรเจกต์ไม่มี test runner → คอมไพล์ด้วย `tsc` ลง scratch dir แล้วรันด้วย node (ตามที่เคยทำกับ `lib/entry-rows.ts`)

**เทสต์ parser:**
- แถวปกติ → ค่าครบทั้ง 6 ฟิลด์
- `Comments = -6` → เก็บเป็น `-6` ไม่ใช่ `0` หรือ `6`
- `Video Views = "undefined"` → ข้ามทั้งแถว (ไม่ใช่บันทึก 0)
- BOM นำหน้าไฟล์ → แถวแรกไม่เพี้ยน
- แถวสั้น/ขาดคอลัมน์ → ไม่ throw
- วันที่อ่านไม่ออก → ข้ามแถว

**เทสต์ aggregation:**
- `statsOn` กับ `orderDate` ที่เป็นวันเดียวกันตามปฏิทินไทย ต้องลงสัปดาห์เดียวกัน (เทสต์นี้คือตัวจับบั๊กสลับ UTC/local)
- สัปดาห์ที่ views = 0 แต่มีออเดอร์ → `convPct === null` ไม่ใช่ `Infinity`
- input ว่าง → คืน array ว่าง ไม่ throw

**ตรวจทั้งระบบ:** `npx tsc --noEmit` + `npm run lint` แล้วรัน dev server แยก (`NEXT_DIST_DIR=.next-dev`, `dev-test.db`, port 3001) อัปไฟล์จริงจาก `data_last28days/` ดูว่าตัวเลขตรงกับที่คำนวณไว้ในสเปกนี้ (24,598 วิว / 56 ออเดอร์ / 0.228%)

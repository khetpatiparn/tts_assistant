# แยกสินค้าที่แคปมาเป็น "ชุด" (CandidateBatch) — ดีไซน์

วันที่: 2026-08-23

## ปัญหา

หน้า "หาสินค้า" เก็บสินค้าที่แคปมาแบบ **แถวเดียวต่อ 1 ชื่อสินค้าตลอดกาล** (`ProductCandidate.nameKey` เป็น `@unique` ทั้งตาราง) เวลาอัปแคปรอบใหม่ `extractCandidates` จะ upsert ทับแถวเดิม สินค้าที่ยังอยู่ในอันดับจะได้ `capturedOn` ใหม่ แต่**สินค้าที่หลุดอันดับไปแล้วจะค้างอยู่ในตารางตลอดไป** โดยไม่มีอะไรบอกว่ามันหลุดไปแล้ว

ผลคือผู้ใช้เปิดหน้ามาแล้วแยกไม่ออกว่าอันไหนคือของที่ขายดีอยู่จริง ณ ตอนนี้ กับอันไหนคือซากจากรอบก่อน — ซึ่งเป็นคำถามเดียวที่หน้านี้มีหน้าที่ตอบ

### หลักฐานจากข้อมูลจริง (dev.db, 2026-08-23)

รวม 162 แถว 4 หมวด แยกตาม "วันที่เก็บล่าสุดของหมวดนั้น":

| หมวด | วันที่เก็บ | อยู่ในรอบล่าสุด | ตกค้างจากรอบเก่า |
|---|---|---|---|
| แผ่นและเสาลับเล็บแมว | 18, 20 ส.ค. | 39 | 6 |
| ของใช้สำหรับสัตว์เลี้ยง | 19, 20 ส.ค. | 40 | 13 |
| ที่เก็บของและชั้นวาง | 20 ส.ค. | 37 | 0 |
| โซฟา | 20, 23 ส.ค. | 21 | 6 |

**ของตกค้าง 25 แถวจาก 162 (15%)** และในนั้น 12 แถวเป็นของที่ผู้ใช้เคยตัดสินไปแล้ว (ปัดตก 8 · สนใจ 3 · ทำคลิปแล้ว 2 ที่ผูก entry จริง)

ตัวเลข "อยู่ในรอบล่าสุด" ที่ได้ 39/40/37/21 ตรงกับลิสต์จัดอันดับจริงของ TikTok Shop ที่ให้ประมาณ 40 อันดับต่อ "ประเภทสินค้า" แปลว่า**การอัปรอบใหม่คือการแทนที่ลิสต์ทั้งลิสต์** ไม่ใช่การเติมทีละตัว

## การตัดสินใจที่ผู้ใช้ยืนยันแล้ว

### 1. ตัดระบบ triage ทิ้งทั้งหมด

ตัด `สนใจ` (interested) และ `ปัดตก` (rejected) ออก เหตุผล:

- **`สนใจ` ไม่ได้ทำอะไรเลยในระบบ** — มี 19 แถวที่ติดไว้ แต่ไม่มีผลต่อการเรียง การกรอง หรือการคิดป้ายแม้แต่จุดเดียว เป็นบุ๊กมาร์กเปล่า
- **`ปัดตก` ทำงานเดียวคือซ่อนแถวออกจากมุมมองดีฟอลต์** — แต่เมื่อระบบเปลี่ยนเป็นแสดงเฉพาะชุดล่าสุด ของที่ไม่เอาจะหลุดออกจากสายตาเองอยู่แล้วตอนหมดรอบ การซ่อนด้วยมือจึงเป็นงานซ้ำซ้อน
- การตัดสองอันนี้คือสิ่งที่**ปลดล็อกให้ชุดข้อมูลแยกขาดจากกันได้จริง** ถ้ายังมี triage อยู่ การแยกชุดจะทำให้ทุกรอบต้องมานั่งไล่ปัดตกใหม่รอบละ ~40 ตัวต่อหมวด ซึ่งทำให้ฟีเจอร์นี้แย่ลงกว่าเดิม

### 2. เก็บ `linkedEntryId` ไว้ — ในฐานะข้อเท็จจริง ไม่ใช่สถานะ

`createEntryFromCandidate` สร้าง `PromptEntry` แล้วผูก id กลับมาที่แถวอยู่แล้ว ค่านี้ถูกเซ็ตโดยระบบตอนกดปุ่ม ไม่ใช่ป้ายที่ผู้ใช้ติดเอง จึงไม่ใช่ triage และไม่ต้องตัดทิ้ง

แถวที่มี `linkedEntryId` จะแสดง **"สร้างแล้ว →"** เป็นลิงก์ไปหน้างานนั้น ประโยชน์คือกันกดสร้างซ้ำในรอบเดียวกัน

**ลบชุดทิ้ง = ลิงก์นี้หายไปด้วย แต่ตัว `PromptEntry` ไม่ถูกลบ** ยังอยู่ในหน้ารายการสินค้าตามปกติ (ไม่มี FK cascade ระหว่างสองตารางนี้ `linkedEntryId` เป็นแค่ `String?` เปล่าๆ) งานจริงที่ทำไปแล้วจึงไม่มีทางหายเพราะลบชุด

### 3. ชุด = 1 ครั้งที่กด "อ่านข้อมูลจากรูป"

พิจารณา 3 ทางแล้วเลือกทางนี้:

- **แทนที่อัตโนมัติรายหมวด** (อัปหมวดไหน ลบของเก่าหมวดนั้นทันที) — ถูกปฏิเสธเพราะมีกับดักจริง: ลิสต์ 40 อันดับต้องแคปหลายใบ ถ้าอัปไม่ครบในครั้งเดียว ของเก่าจะถูกลบทิ้งแล้วเหลือเท่าที่อัปมา กู้คืนไม่ได้
- **ถามก่อนแทนที่** — สะอาดแต่เพิ่มขั้นตอนถามทุกครั้ง
- **ชุดแยกขาด + ลบเองได้** ← เลือกอันนี้ ไม่มีกับดัก ควบคุมเองได้เต็มที่ และเมื่อดีฟอลต์แสดงเฉพาะชุดล่าสุดต่อหมวด การสะสมชุดเก่าก็ไม่กวนสายตาแม้ยังไม่ได้ลบ

## โครงสร้างข้อมูล

### ตารางใหม่ `CandidateBatch`

```prisma
model CandidateBatch {
  id         String             @id @default(cuid())
  /// เวลาที่กดอ่านข้อมูลจากรูป — ใช้ตัดสินว่าชุดไหนใหม่กว่า
  capturedOn DateTime
  createdAt  DateTime           @default(now())
  rows       ProductCandidate[]

  @@index([capturedOn])
}
```

ไม่เก็บ `categoryLabel` ที่ระดับชุด เพราะ 1 ชุดมีได้หลายหมวด (ผู้ใช้แปะแคปหลายหมวดพร้อมกันได้) — หมวดยังคงอยู่ที่ระดับแถวเหมือนเดิม การแสดงผลจะสรุปหมวดจากแถวในชุดเอง

### เปลี่ยน `ProductCandidate`

```prisma
model ProductCandidate {
  id            String   @id @default(cuid())
  batchId       String
  batch         CandidateBatch @relation(fields: [batchId], references: [id], onDelete: Cascade)
  name          String
  /// normalizeName(name) — unique ต่อชุด ไม่ใช่ทั้งตาราง
  nameKey       String
  price         Float
  commission    Float
  weeklySales   Int?
  categoryLabel String
  capturedOn    DateTime
  note          String   @default("")
  linkedEntryId String?
  createdAt     DateTime @default(now())

  @@unique([batchId, nameKey])
  @@index([categoryLabel])
  @@index([batchId])
}
```

การเปลี่ยนแปลง:

- **เพิ่ม** `batchId` + relation `onDelete: Cascade` — ลบชุดแล้วแถวหายตาม
- **ลบคอลัมน์ `status`** และ index ของมัน
- **`nameKey` เปลี่ยนจาก `@unique` ทั้งตาราง เป็น `@@unique([batchId, nameKey])`** — สินค้าชื่อเดียวกันอยู่คนละชุดได้ แต่ในชุดเดียวกันยังกันซ้ำอยู่ (สำคัญ เพราะแคปแบบเลื่อนจอมักมีสินค้าซ้ำตรงรอยต่อระหว่างภาพ)
- `capturedOn` ที่ระดับแถวยังอยู่ ค่าเท่ากับของชุดเสมอ เก็บไว้เพื่อให้ query รายแถวไม่ต้อง join

## พฤติกรรมตอนอ่านข้อมูลจากรูป

`extractCandidates` เปลี่ยนจาก upsert เป็น:

1. สร้าง `CandidateBatch` 1 แถว (`capturedOn = new Date()`)
2. สร้าง `ProductCandidate` ทุกแถวที่อ่านได้ ผูกกับชุดนั้น — **ไม่แตะชุดเก่าเลย**
3. ถ้าในผลลัพธ์ครั้งนั้นมีชื่อซ้ำกันเอง (รอยต่อภาพ) ให้ทับกันภายในชุดตาม `@@unique([batchId, nameKey])` เหมือนพฤติกรรมเดิม
4. ถ้าไม่มีแถวที่อ่านได้เลย (`rows.length === 0`) **ต้องไม่สร้างชุดเปล่าค้างไว้** — ให้ throw ตามเดิมโดยไม่สร้าง batch

ค่าที่คืนกลับเปลี่ยนจาก `{ added, updated, skipped }` เป็น `{ batchId, added, skipped }` เพราะไม่มีการ update ข้ามชุดอีกแล้ว

## พฤติกรรมหน้าเว็บ

### มุมมองดีฟอลต์: เฉพาะชุดล่าสุดของแต่ละหมวด

หน้าแสดงแถวจาก **ชุดล่าสุดของแต่ละ `categoryLabel`** เท่านั้น

นิยาม "ชุดล่าสุดของหมวด X" = ในบรรดาชุดที่มีแถวของหมวด X ให้เอาชุดที่ `capturedOn` มากที่สุด

นี่คือส่วนที่แก้ปัญหาต้นเรื่องโดยตรง: พออัปรอบใหม่ ของที่หลุดอันดับจะหายจากสายตาทันทีโดยผู้ใช้ไม่ต้องทำอะไร

ผู้ใช้เลือกดูชุดใดชุดหนึ่งเจาะจงได้จากรายการชุด (ดูหัวข้อถัดไป)

### ตัวกรอง

ตัวกรอง 5 ปุ่มเดิม (ยังไม่ปัดตก / ยังไม่ตัดสิน / สนใจ / ปัดตกแล้ว / ทั้งหมด) ถูกแทนด้วย 3 ปุ่ม:

| ปุ่ม | เงื่อนไข |
|---|---|
| ทั้งหมด (ดีฟอลต์) | ไม่กรอง |
| ยังไม่ได้สร้าง | `linkedEntryId === null` |
| สร้างแล้ว | `linkedEntryId !== null` |

### ป้ายแนะนำ: ท็อป 3 คิดภายในชุด × หมวด

- `TOP_BADGE_COUNT` เปลี่ยนจาก **4 เป็น 3**
- `pickCandidateBadges` เปลี่ยนจากจัดกลุ่มด้วย `categoryLabel` อย่างเดียว เป็นจัดกลุ่มด้วย **`batchId` + `categoryLabel`**
- เกณฑ์คัดสิทธิ์เหลือแค่ `isCommissionPercentPlausible(commissionPercent)` (เดิมมี `status !== "rejected"` ด้วย ซึ่งหายไปพร้อมคอลัมน์ status)
- การจัดอันดับไม่เปลี่ยน: `ยอดขายดี` เรียงตาม `weeklySales` · `ค่าคอม/ชิ้นสูงสุด` เรียงตาม `commission` เป็นบาทจริง

การผูกป้ายกับชุดสำคัญ เพราะป้ายคือ "อันดับในลิสต์นี้" ถ้าปล่อยให้ข้ามชุด ของเก่ากับของใหม่จะมาแย่งอันดับกันซึ่งไม่มีความหมาย

### รายการชุด + ปุ่มลบ

แผง "เก็บมาแล้วในระบบ" เดิม (ที่เป็นชิปรายหมวดใช้กรอง) เปลี่ยนเป็น **รายการชุด** แต่ละรายการแสดง:

- หมวดที่อยู่ในชุดนั้น พร้อมจำนวนแถวต่อหมวด (เช่น `โซฟา 21`)
- วันที่เก็บ
- ป้าย "ล่าสุด" ถ้าเป็นชุดล่าสุดของหมวดนั้น
- ปุ่ม **ดู** (กรองหน้าให้เหลือเฉพาะชุดนี้) และปุ่ม **ลบชุดนี้**

ปุ่มลบต้องมีการยืนยันก่อน 1 ขั้น เพราะเป็นการลบถาวรและ `dev.db` ไม่มี backup — ข้อความยืนยันต้องบอกจำนวนแถวที่จะหายและเตือนว่าแถวที่ "สร้างแล้ว" จะเสียลิงก์ไป (แต่ตัวงานไม่หาย)

## การย้ายข้อมูลเดิม (162 แถว)

ไม่ทิ้งข้อมูลเดิม — จัดเข้าชุดตามที่มันแยกได้อยู่แล้ว

ขั้นตอนใน migration:

1. สร้าง `CandidateBatch` หนึ่งชุดต่อทุกค่า **(วันที่ของ `capturedOn`)** ที่มีอยู่จริง โดยใช้ `capturedOn` ที่เก่าที่สุดของวันนั้นเป็นค่าของชุด
2. ผูกทุกแถวเข้ากับชุดของวันตัวเอง
3. ทิ้งคอลัมน์ `status`

จัดกลุ่มด้วย "วัน" ไม่ใช่ "วัน + หมวด" เพราะ 1 ชุดมีได้หลายหมวดโดยนิยาม และการอัปในวันเดียวกันคือรอบเดียวกันจริงตามการใช้งาน จากข้อมูลจริงจะได้ **4 ชุด** (18, 19, 20, 23 ส.ค.)

ผลลัพธ์ที่ตรวจสอบได้หลัง migrate: จำนวนแถวรวมยังเป็น 162 · ทุกแถวมี `batchId` · แถวที่มี `linkedEntryId` ยังครบ 5 แถว

## สิ่งที่ถูกลบออกจากโค้ด

- คอลัมน์ `ProductCandidate.status` และ `@@index([status])`
- Server Action `setCandidateStatus`
- ค่าคงที่/ตัวกรองสถานะใน `components/candidates-route.tsx` (`FILTERS` ชุดเดิม, `StatusFilter`)
- ปุ่ม "สนใจ" และ "ปัดตก"
- การเซ็ต `status: "done"` ใน `createEntryFromCandidate` (เหลือเซ็ต `linkedEntryId` อย่างเดียว)
- พารามิเตอร์ `status` ใน `pickCandidateBadges`

## สิ่งที่ไม่ทำในรอบนี้

- ไม่ทำการรวมข้อมูลข้ามชุด (เช่น "สินค้านี้อยู่ในอันดับมากี่รอบแล้ว") — เป็นคนละปัญหาและยังไม่มีความต้องการจริง
- ไม่ทำการลบชุดเก่าอัตโนมัติ/ตั้งเวลา — ผู้ใช้กดลบเอง
- ไม่แตะการสกัดข้อมูลด้วย AI (`lib/gemini.ts`) และ `parseCandidateRows`
- ไม่แตะเลย์เอาต์ตารางที่เพิ่งทำเสร็จ (commit `e4306a1`) นอกจากคอลัมน์ปุ่มและตัวกรอง

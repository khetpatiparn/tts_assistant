# แผนสัปดาห์ (Weekly Plan & Evaluation) — Design

## Problem

ผู้ใช้ทำคลิปไม่สม่ำเสมอ **ไม่ใช่เพราะไม่รู้ว่าต้องทำอะไร แต่เพราะทำแล้วไม่เห็นว่าคืบหน้าจริงไหม** — คำพูดของผู้ใช้เอง: "ถ้ามันไม่มีอะไรที่รู้ว่าเราทำไปแล้วก้าวหน้าขึ้นจริงๆ จะทำไปทำไม มันเหมือนกับเราทำไปเรื่อยๆ จนเราไม่รู้เลยว่าเราทำอะไรแล้วก็ลืมไป"

ระบบปัจจุบันมี `lib/recommender.ts` (การ์ด "ควรทำอะไรต่อ" ในแท็บ ④) ที่ออกสัญญาณ **ต่อคลิป** แบบ reactive แต่ไม่มี 3 อย่างที่ขาด:

1. **แผนระดับสัปดาห์** — ควรทำ winner ตัวไหนซ้ำ ทดสอบอะไร ตั้งเป้ากี่คลิป
2. **ความจำ** — ไม่เก็บว่าเคยแนะนำอะไรไว้ จึงย้อนประเมินไม่ได้
3. **การประเมินย้อนหลัง + เหตุผล** — "สิ่งที่ทำสัปดาห์ก่อนได้ผลไหม เพราะอะไร"

เป้าหมายคือปิด loop: **รู้ว่าตอนนี้อยู่ตรงไหน → ควรทำอะไรต่อ (พร้อมเหตุผล) → ลงมือ → สัปดาห์ถัดไปเห็นผลจริงว่าเวิร์กไหม → สะสมเป็นบทเรียน**

## แนวทางที่เลือก (และที่ตัดทิ้ง)

พิจารณา gamification เต็มรูปแบบ (streak/badge/level/XP) แล้ว **ตัดออกทั้งหมด** ตามการตัดสินใจของผู้ใช้: ต้องการ "ระบบดีๆ ตัวหนึ่งที่ใช้งานง่าย มี UX ที่ดี การจัดวางที่โอเค flow ลำดับถูกต้อง" ไม่ใช่เกม

เหตุผลเชิงหลักฐานที่สนับสนุนการตัด: งานวิจัย gamification เตือนว่าแต้ม/badge ที่ไม่ผูกกับผลจริงสามารถ**บั่นทอน**แรงจูงใจภายใน (overjustification effect) และ streak ที่ไม่มี safety net ทำให้เกิด shame/burnout — สำหรับเคสนี้ยังมีความเสี่ยงเฉพาะตัวคือ **การเร่งจำนวนคลิปอาจทำให้ข้ามขั้น transform** ซึ่งเป็นต้นเหตุ violation "unoriginal content" ที่เพิ่งเกิดเมื่อ ก.ค. 2026

สิ่งที่เก็บไว้จากการวิเคราะห์นั้นคือหลักการที่ไม่ต้องเป็นเกมก็ใช้ได้:
- **Autonomy** — แผนเป็น "ข้อเสนอ" ไม่ใช่คำสั่ง: ข้าม/แก้/เพิ่มรายการเองได้ทุกข้อ โดยไม่มีข้อความตำหนิ
- **Competence** — บอก "เพราะอะไรจึงเสนอ" และ "เพราะอะไรจึงไม่เสนออีกแบบ" เพื่อให้ผู้ใช้เข้าใจเกม ไม่ใช่แค่ทำตาม
- **Progress ที่จับต้องได้** — แสดงผลลัพธ์จริงเป็นตัวเลข (คลิป/รายได้/winner) ไม่ใช่แต้มสมมติ

## ข้อเท็จจริงจากโค้ด/ข้อมูลจริง (load-bearing — ตรวจสอบแล้ว 2026-07-26)

### โครงสร้างที่มีอยู่
- `components/workspace-tabs.tsx` มี 4 แท็บ (`brief | production | core | dashboard`) — `WorkspaceTab` เป็น union type จุดเดียว
- `components/prompt-workspace.tsx:104` `useState<WorkspaceTab>("brief")` คือแท็บเริ่มต้น · บรรทัด 186/211 สลับไป `brief` เมื่อเลือก entry จาก sidebar (พฤติกรรมนี้ต้องคงไว้)
- `app/page.tsx` เป็น Server Component ที่ดึงข้อมูลทั้งหมดแล้วส่งลง `PromptWorkspace` — ที่เดียวที่คำนวณ `lastImportedAt` (บรรทัด 35-39)
- `lib/recommender.ts` (pure) ให้สัญญาณต่อคลิป — **นำมาใช้ต่อในแผนได้ ไม่ต้องเขียนใหม่** · `lib/dashboard.ts` เป็นเจ้าของ `IMPORT_STALE_DAYS = 7` และ `summarizeOrders`

### ข้อบกพร่องเดิมที่ต้องแก้ (พบระหว่างออกแบบ)
- **`lastImportedAt` คำนวณจาก `AffiliateOrder` เท่านั้น** (`app/page.tsx:36`) — อัปแค่ไฟล์รายได้ก็รีเซ็ตคำเตือน ทั้งที่ข้อมูลวิวอาจเก่าหลายสัปดาห์ · ตาราง `ClipMetric` และ `FollowerActivity` มีคอลัมน์ `importedAt` อยู่แล้ว **จึงไม่ต้องเพิ่ม schema** แค่คำนวณเพิ่ม 2 ค่า

### ข้อจำกัดของแหล่งข้อมูล (วัดจากไฟล์จริง)
- **Content.csv จาก TikTok Studio ให้สูงสุด 15 แถวเสมอ** ไม่ว่าเลือกช่วง 7/28/60/365 — ยืนยันจากไฟล์จริง 2 รอบ (ช่วง 60 วันได้ 15 แถวเรียงตามวิวมาก→น้อย 67,703→1,159 · ช่วง 7 วันได้ 15 แถวคนละชุด มีคลิปวิวต่ำถึง 321)
- **การอัปหลายช่วงในวันเดียวกัน "รวมกัน" ได้** เพราะ `ClipMetric` unique ที่ `(videoId, capturedOn)` และ `capturedOn` มาจากคอลัมน์ `Time` ในไฟล์ (= วันที่ export) — พิสูจน์แล้ว: snapshot 2026-07-26 มี 23 คลิป จากการอัป 2 ไฟล์ (15+15) → **กลยุทธ์ union of windows ใช้ได้จริง**
- **การนำเข้าทั้ง 3 ไฟล์เป็น upsert** (`app/actions.ts` — `affiliateOrder.upsert` by `orderId`, `clipMetric.upsert` by `(videoId, capturedOn)`, `followerActivity.upsert` by `(activityOn, hour)`) → อัปทับช่วงเดิมปลอดภัย และ**อัปเดตสถานะออเดอร์ย้อนหลัง** (รอ→ชำระแล้ว) จึงควรเลือกช่วงกว้างที่สุดเสมอสำหรับไฟล์รายได้
- **ความครอบคลุมปัจจุบัน:** 55 entries · 52 มี videoUrl · **24 มีข้อมูลวิว** · 30 มีออเดอร์ · ออเดอร์ 269 แถว จับคู่ได้ 268
- **selection bias วัดได้จริง:** median วิว 1,828 (ตอนมีแต่ท็อป 15) → 1,538 (หลังเติมคลิปวิวน้อย) และค่าต่ำสุดที่เห็น 1,038 → 321 — `median` คือค่าที่ `detectSignals` ใช้เป็นเกณฑ์ (`reachEnough = max(500, median*2)`) จึงเคยตั้งสูงเกินจริง
- **`buildClipStats` ข้าม entry ที่ไม่มี snapshot** (`recommender.ts:77`) — ระบบเดิม**ไม่เคย**เดาว่า "ไม่มีข้อมูล = 0 วิว" ซึ่งถูกต้องแล้ว **ต้องรักษาพฤติกรรมนี้ไว้**

### ข้อมูลเชิงธุรกิจที่พบ (ใช้เป็นตัวอย่าง/ทดสอบความสมเหตุสมผลของแผน)
- รายได้ settled กระจุกที่ "ที่ลับเล็บแมว" 1,914 บาท (~71% ของทั้งช่อง) · winner รองคือ ชั้นวางของ 5 ชั้น (217) · โต๊ะรีดผ้า (159)
- **สินค้าหมวดแมวครองรายได้** (ที่ลับเล็บ · ที่นอนแมว · ของเล่นแมว · บ้านแมว · คอนโดแมว) ขณะที่ของแต่งบ้านที่ได้วิวสูงอย่างผ้าม่าน (3,486 วิว) ขายไม่ได้เลย
- จำนวนคลิปต่อสัปดาห์แกว่งมาก: W24=3 · W25=6 · W26=5 · W27=3 · W28=23 · W29=9

## Design

### ภาพรวม

แท็บใหม่ **"① แผนสัปดาห์"** วางเป็นแท็บแรกและเป็นแท็บเริ่มต้นตอนเปิดแอป (แท็บเดิมเลื่อนเป็น ②-⑤) — ผู้ใช้เปิดแอปมาเห็น "ตอนนี้อยู่ตรงไหน / ต่อไปทำอะไร" ก่อนเสมอ แล้วคลิกเดียวไปทำงานต่อ · การเลือก entry จาก sidebar ยังสลับไปแท็บ Brief เหมือนเดิม

หน้าแบ่งเป็น 3 ส่วนเรียงตาม flow การอ่าน:

```
┌ ① ตอนนี้ ─────────────────────────────────────┐
│  สัปดาห์นี้ (21-27 ก.ค.)                        │
│  คลิปที่ลง 4 · เป้า 6      รายได้ 7 วัน 1,240฿  │
│  ข้อมูล: รายได้ วันนี้ · วิว วันนี้ · ผู้ติดตาม 24 วัน │
│  ครอบคลุมข้อมูลวิว 24/52 คลิป                    │
├ ② ทำอะไรต่อ ──────────────────────────────────┤
│  ☑ ทำ "ที่ลับเล็บแมว" ซ้ำ angle ใหม่             │
│     เพราะ: 1,914฿ (71% ของรายได้) ยังไม่ตก        │
│  ☐ ทดสอบสินค้าหมวดแมว 1 ตัว        [ข้าม] [แก้]  │
│     เพราะ: 5 ใน 6 winner เป็นของแมว              │
│     ระวัง: อย่าเลือกสินค้าที่ต้องใช้รูปคน          │
│  + เพิ่มสิ่งที่อยากทำเอง                          │
├ ③ สัปดาห์ที่แล้ว ─────────────────────────────┤
│  ทำ 9 คลิป (เป้า 6) · รายได้ 2,110฿ (+18%)      │
│  ✓ ที่ลับเล็บแมว angle ใหม่ → +412฿              │
│  ✗ ผ้าม่าน → 3,486 วิว 0 ขาย                    │
│  สรุป: หมวดแมวยังเป็นจุดแข็ง ของแต่งบ้าน...      │
│  บทเรียนสะสม (5)                    [ดูทั้งหมด]  │
└────────────────────────────────────────────────┘
```

### ส่วนที่ ① "ตอนนี้" — สถานะปัจจุบัน

ตัวเลขที่คำนวณด้วยโค้ดล้วน (ไม่มี AI):
- สัปดาห์ปัจจุบัน (จันทร์–อาทิตย์ เวลาไทย) · จำนวนคลิปที่ลงแล้วในสัปดาห์นี้เทียบเป้า
- รายได้ settled 7 วันล่าสุด
- **ความสดของข้อมูลแยกรายไฟล์** (แก้ข้อบกพร่องเดิม): รายได้ / วิวคลิป / ผู้ติดตาม แต่ละอันบอกว่านำเข้าเมื่อกี่วันก่อน
- **ความครอบคลุมข้อมูลวิว** (`x/y คลิป`) — เพื่อไม่ให้ผู้ใช้เชื่อสถิติเกินจริง

### ส่วนที่ ② "ทำอะไรต่อ" — รายการแนะนำ

- แต่ละรายการมี **หัวข้อ · "เพราะ:" (เหตุผล) · "ระวัง:" (ข้อควรระวัง/ทำไมไม่ควรเลือกอีกแบบ)** — ช่อง "ระวัง" ว่างได้
- สถานะ 3 แบบ: `ยังไม่ทำ / ทำแล้ว / ข้าม` — ติ๊กเองด้วยมือ (ไม่ auto-detect เพราะการผูกคลิปใหม่กับรายการโดยอัตโนมัติเดาผิดได้ง่าย)
- **ปรับได้ทุกข้อ:** แก้ข้อความ · ใส่โน้ตของตัวเอง · ข้ามโดยไม่มีข้อความตำหนิ · **เพิ่มรายการของตัวเอง** (สำคัญ: ผู้ใช้ระบุว่าจะทำตาม AI บ้าง ทำตามที่อยากเองบ้าง)
- ชนิดรายการ (`kind`) มี 4 แบบเพื่อให้ประเมินย้อนหลังได้: `repeat` (ทำ winner ซ้ำ) · `test` (ทดสอบสินค้าใหม่) · `volume` (เป้าจำนวนคลิป) · `safety` (ข้อควรระวัง เช่น ทุกคลิปผ่าน transform)
- รายการ `repeat` ผูก `entryId` ได้ → คลิกไปที่ entry นั้นเพื่อกด "ทำซ้ำ" ต่อได้ทันที (เชื่อมกับฟีเจอร์ duplicate ที่มีอยู่)

**เป้าจำนวนคลิป (`clipTarget`) — ขึ้นช้า ลงง่าย:** คำนวณจากค่ามัธยฐาน 4 สัปดาห์ล่าสุด ปรับขึ้นได้ไม่เกิน +1 ต่อสัปดาห์ แต่ลดลงได้ทันทีตามความเป็นจริง — กันไม่ให้สัปดาห์ที่ทำได้ดี (เช่น W28=23) กลายเป็นเพดานที่ต้องเอาชนะตลอดไป ผู้ใช้แก้ตัวเลขเองได้

### ส่วนที่ ③ "สัปดาห์ที่แล้ว" — ประเมินผล + บทเรียน

- ตัวเลขเทียบสัปดาห์ก่อนหน้า (คลิป / รายได้ settled / winner ใหม่) — **โค้ดคำนวณ**
- ผลรายข้อของแผนสัปดาห์ก่อน: ทำแล้ว/ข้าม + ผลจริงที่วัดได้ (วิว/ออเดอร์/รายได้ของคลิปที่ผูกกับรายการนั้น)
- **สรุปเชิงเหตุผล ("เพราะอะไร")** — AI เขียน 2-4 ประโยค
- **บทเรียนสะสม** — รายการข้อสรุปพร้อมสถานะ `works / fails / unclear` + จำนวนครั้งที่ยืนยัน + หลักฐานเชิงตัวเลข ลบทิ้งได้ถ้าเห็นว่าผิด

### การแบ่งงาน: โค้ด vs AI

| งาน | ใครทำ |
|---|---|
| คำนวณตัวเลขทุกชนิด (คลิป/รายได้/วิว/ความสดข้อมูล/เป้า) | **โค้ดล้วน** (`lib/weekly-plan.ts`, pure) |
| ตัดสินว่ารายการสัปดาห์ก่อน "ได้ผล" ไหม | **โค้ดล้วน** (เทียบตัวเลขตามกฎ) |
| เขียนสรุปเชิงเหตุผล + เสนอรายการใหม่ + ปรับปรุงบทเรียน | **AI (Gemini)** |

เหตุผล: ถ้าปล่อยให้ AI คำนวณเลขเอง มันจะเริ่มมั่วตัวเลขแล้วผู้ใช้จะเชื่อระบบไม่ได้อีกเลย — AI ได้รับตัวเลขที่คำนวณเสร็จแล้วเป็น input เท่านั้น

### ประตูข้อมูล (data gate)

ก่อนกด "สร้างแผนสัปดาห์นี้" ต้องมีข้อมูลสด:

| ไฟล์ | ระดับ | เหตุผล |
|---|---|---|
| รายได้ (xlsx) | **บังคับ** ≤7 วัน | เป็นตัววัดผลหลัก และข้อมูลออเดอร์ครบ 100% |
| วิวคลิป (Content.csv) | **บังคับ** ≤7 วัน | ขาดแล้วประเมินคลิปทดสอบไม่ได้ |
| ผู้ติดตาม (FollowerActivity.csv) | ไม่บังคับ (เตือน ≤30 วัน) | เปลี่ยนช้า ใช้แค่วิเคราะห์เวลาโพสต์ |

ถ้าไม่ผ่าน → ปุ่มปิด พร้อมบอกว่าขาดไฟล์ไหนและ**ลิงก์ไปยังฟอร์มอัปโหลดในแท็บรายได้**

**คำแนะนำการ export ที่แสดงในประตูข้อมูล** (สรุปจากข้อจำกัดจริงด้านบน):
- รายได้ xlsx → เลือกช่วงกว้างสุด · ทุกสัปดาห์
- Content.csv → **export 2 ครั้งในวันเดียวกัน: ช่วง 7 วัน แล้วช่วง 365 วัน** (เพดาน 15 แถว/ครั้ง แต่รวมกันเป็น snapshot เดียวที่ครอบคลุมกว่า)
- FollowerActivity.csv → ช่วง 365 วัน · เดือนละครั้ง
- **เตือนเพิ่มเมื่อสัปดาห์นั้นลงคลิป > 12 ตัว** ให้ export Content กลางสัปดาห์อีกรอบ (ไม่งั้นคลิปวิวน้อยหลุดเพดาน 15)

### Data model (Prisma)

```prisma
model WeeklyPlan {
  id         String     @id @default(cuid())
  weekStart  DateTime   @unique   // จันทร์ 00:00 เวลาไทย เก็บเป็น UTC (แบบเดียวกับ postedAt)
  clipTarget Int
  summary    String     @default("")  // สรุป "เพราะอะไร" ของสัปดาห์ก่อน (AI)
  model      String     @default("")  // โมเดลที่ใช้สร้าง
  createdAt  DateTime   @default(now())
  items      PlanItem[]
}

model PlanItem {
  id        String     @id @default(cuid())
  planId    String
  plan      WeeklyPlan @relation(fields: [planId], references: [id], onDelete: Cascade)
  kind      String                    // repeat | test | volume | safety
  title     String
  reason    String     @default("")
  caution   String     @default("")
  entryId   String?                   // ผูก entry เดิม (kind=repeat) — ไม่ทำ FK relation
  status    String     @default("open")  // open | done | skipped
  note      String     @default("")   // โน้ตของผู้ใช้เอง
  source    String     @default("ai") // ai | user
  sortOrder Int        @default(0)
}

model Lesson {
  id        String   @id @default(cuid())
  statement String   @unique   // "สินค้าหมวดแมวขายได้"
  verdict   String              // works | fails | unclear
  evidence  String   @default("")
  timesSeen Int      @default(1)
  updatedAt DateTime @updatedAt
}
```

**`entryId` ไม่ทำเป็น FK relation** — entry ถูกลบได้ และแผนเก่าควรเก็บประวัติไว้แม้ entry หาย (ต่างจาก `AffiliateOrder` ที่ใช้ `SetNull`) โค้ดที่อ่านต้องเผื่อกรณีหา entry ไม่เจอ

### กฎการประเมิน (โค้ด)

- **รายการ `repeat`/`test` ที่ติ๊ก "ทำแล้ว"** → หา entry ที่สร้างในสัปดาห์นั้นและตรงกับสินค้า/ผูก `entryId` → รายงานวิว+ออเดอร์+รายได้ที่เกิดขึ้น
- **"winner ใหม่"** = entry ที่เพิ่งมีออเดอร์ settled เป็นครั้งแรกในสัปดาห์นั้น
- **ห้ามสรุปว่า "ไม่เวิร์ก" เมื่อไม่มีข้อมูลวิว** — ต้องแสดงว่า `ยังไม่มีข้อมูลวิว` แยกจาก `วิวน้อย` (สอดคล้องกับพฤติกรรมเดิมของ `buildClipStats`)
- คลิปที่ยังไม่ถึง 7 วันหลังโพสต์ ให้ทำเครื่องหมาย "ยังเร็วเกินสรุป"

## Non-goals (YAGNI / เฟส 2)

- **ไม่ทำ gamification** — streak, badge, level, XP, แต้ม (ตัดตามการตัดสินใจของผู้ใช้ · ถ้าเฟส 1 ยังไม่พอค่อยเติมทีหลัง ข้อมูลรองรับอยู่แล้ว)
- ไม่ทำ notification/reminder นอกแอป
- ไม่ auto-import (TikTok ไม่มี API ต้องโหลดมือ)
- ไม่ auto-detect ว่าคลิปไหนตรงกับรายการไหน (ให้ติ๊กเอง)
- ไม่เชื่อมทีม Creator Camp / ไม่ทำ social
- ไม่ทำนายรายได้ล่วงหน้า
- ไม่แตะ `lib/recommender.ts` (นำมาใช้ต่อ ไม่แก้ตรรกะเดิม)
